## 4. 人天估算

说明：

- 1 人天按“1 人较完整投入 1 天”估算。
- 当前时间紧，估算按“能汇报版”而非“论文式精修版”。
- 若多人并行，可压缩自然日；若核心工作仍主要由组长承担，则自然日压力会显著增大。

| 工作包 | 估算人天 | 说明 |
|---|---:|---|
| W1 冻结范围 | 0.3 | 需要快速定边界，避免后续返工 |
| W2 业务对象识别 | 0.8 | 包括对象清单、定义与来源依据 |
| W3 关系梳理 | 0.7 | 决定类图复杂度 |
| W4 核心业务类图 | 1.5 | 本阶段最重单项，含 2 轮修订 |
| W5 数据采集入库脚本 | 0.4 | 先文字脚本，再转图 |
| W6 门户认领审核脚本 | 0.4 | 同上 |
| W7 检索请求处理脚本 | 0.5 | 一般最复杂 |
| W8 三张时序图建模 | 1.8 | 含 3 图绘制与统一风格 |
| W9 一致性检查 | 0.8 | 类图/时序图/需求口径互查 |
| W10 需求分析报告 | 1.0 | 展示版，非终稿精修版 |
| W11 汇报 PPT | 0.8 | 8-10 页，含截图与讲述顺序 |
| W12 AI 使用声明 | 0.2 | 可快速完成 |
| W13 彩排与问答准备 | 0.5 | 至少 1 次全流程彩排 |
| 合计 | **9.7 人天** | 能汇报版最低工作量 |

折算建议：

- 若 5 人有效投入：约 2 天可出第一版，4-5 天可收口到汇报版。
- 若 3 人有效投入：自然日会拉长到 3-4 天才出第一版，风险明显上升。
- 若核心仍主要由你单人兜底：工作量相当于连续高强度 3 天以上，风险偏高。

## 7. 当前最大风险：到底是什么

### 风险 1：当前没有需求分析阶段基线

仓库里现在没有现成的 `工作区/需求分析/` 交付物，也没发现可直接复用的需求分析报告、类图、三张时序图底稿。

这意味着：

- 本轮不是“修修改改”，而是要新起一套分析成果；
- 不能按上次需求建模那种“在现有模型上增量修订”的工作量来预估；
- 如果还按“有底稿可改”来排期，时间会被严重低估。

### 风险 2：很容易做过头

需求分析阶段只要求：

- 业务对象识别
- 核心业务类图
- 三张关键时序图
- 与 SRS/需求建模一致性

不要求你现在就把：

- 数据库表设计
- 微服务架构
- 接口协议细节
- 全量异常分支

全做完。

### 风险 3：多人并行后语义漂移

本阶段虽然是并行分工，但三张时序图和报告/PPT 都依赖同一套对象命名与边界定义。

如果组长没有先把业务对象清单、类候选集和流程脚本定死，就会出现：

- 每个人给同一对象起不同名字；
- 时序图参与者和类图主类对不上；
- 报告里术语和图面术语不一致；
- 最终合并成本高于单人重做。

一句话：**这轮不是怕大家没活干，而是怕大家各干各的，最后很难合。**
