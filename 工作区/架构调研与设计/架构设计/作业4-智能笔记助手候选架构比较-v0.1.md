# 作业 4 · 智能笔记助手候选架构比较

> 版本：v0.1（首轮比较稿）
> 状态：推荐方向已记录，待组内确认部署假设和运行边界
> 比较依据：[架构攸关需求清单 v0.1](作业4-智能笔记助手架构攸关需求清单-v0.1.md)
> 项目：智能笔记助手

## 1. 比较目标与边界

本稿比较会实质影响系统逻辑边界和部署方式的候选架构，作为后续架构视图和关键场景走查的输入。比较基线是当前需求分析 v0.2、三条定稿流程，以及前期技术调研和局部实验。

本轮比较**不**确定数据库产品、向量库、消息队列、云模型供应商或具体框架；也不把作业设计稿写成已经实现的产品。由于并发量、数据规模、运行环境和性能门槛仍待确认，不采用无依据的数字打分或宣称某候选达到生产级 SLA。

### 1.1 已知架构约束

1. 检索必须先按用户、工作区、文档范围和有效版本过滤权限，再进行召回、排序和证据组装。
2. 外部模型不是权限判断者。只有证据契约合格、策略允许且用户对本次涉及的文件/版本完成确认后，才可发送证据；不满足条件时留在本地证据、原文、复核或拒答路径。
3. 回答引用须由系统独立核验，能回到本次授权证据和正确文档版本；模型返回“answered”不等于引用有效。
4. 文档处理要区分登记、解析、索引和可检索状态；索引不可用时仍可阅读原文，不得报告入库完成。
5. 笔记保存、导出与分享须保留有效定位并服从权限；失效引用要显式呈现。
6. 本地生成模型未进入一期候选；现有云端调用结果不能证明生产问答质量、服务等级、成本或合规性。

## 2. 候选方案

候选 A 和 B 的主要差异是本地边界内的任务处理方式及外部问答路径；候选 C、D 用于比较不同的信任边界和部署拆分程度。

### 候选 A：本地单机模块化单体

- 一个本地应用包含导入、解析编排、索引、检索、权限、笔记、引用和导出等逻辑模块。
- 文档、索引和笔记保存在用户设备或一台本地服务器；解析/索引任务由同一应用进程或本机后台任务执行。
- 默认不调用外部模型；如后续开放云问答，仍必须走独立的策略门控和证据适配器。
- 适合单用户、本地试用、离线优先；多用户协作和集中运维能力取决于后续部署补充。

### 候选 B：证据治理核心 + 异步任务边界的模块化单体（推荐方向）

- 一个模块化应用承载身份/权限、文档版本、检索、证据契约、笔记、引用校验和策略治理。
- 解析与索引作为可追踪的异步任务；初始可以与应用同机运行，确认确有负载或隔离需要后再拆成独立 worker 进程。
- 原文、结构化内容、全文/语义索引和任务状态按职责持久化；数据库、对象存储和索引产品暂不指定。
- 云端问答只作为可替换适配器，位于权限/版本过滤、证据门控和用户逐文件确认之后；不可用时返回本地检索和原文能力。
- 逻辑模块保持清晰，但不以模块数量推导微服务数量。可覆盖单机演示，也可在用户规模和运行目标确认后演进为共享部署。

### 候选 C：云端托管优先

- 文档处理、OCR、索引和问答主要交给外部托管服务；本系统保留界面、工作区、权限配置和部分业务状态。
- 依赖供应商接口、服务条款、数据保留承诺、网络和服务可用性。
- 即使采用托管处理，也必须先执行本系统授权和外发策略，并保留源版本、证据映射和引用校验。
- 当前仅作为对照，不建议作为敏感/未确认文档的默认路径。

### 候选 D：本地证据层 + 独立微服务

- 保留本地解析、权限、索引、证据与笔记治理，并将导入、检索、笔记、模型网关等拆为独立服务。
- 通过 API 和消息机制协作，允许按服务独立部署、扩缩和故障隔离。
- 需要明确服务间身份传播、权限复核、任务一致性、证据版本、重试幂等、链路追踪和部署运维。
- 这是候选 B 的潜在演进方向；目前没有规模、独立团队或 SLA 证据证明应从第一版开始承担该复杂度。

## 3. 定性比较

说明：“较适合”表示该结构较容易支持对应质量目标，不表示目标已通过实现验证；“有条件”表示依赖额外设计或尚未确定的输入；“弱项”表示候选默认形态与需求存在明显张力。此表是架构推理，不是实验测得的性能排名。

| ASR | A 本地单机模块化单体 | B 模块化单体 + 异步任务/受控问答 | C 云端托管优先 | D 本地证据层微服务 |
|---|---|---|---|---|
| ASR-01 授权隔离 | 较适合；单一信任边界较简单，仍需对每次请求和撤权复核 | 较适合；治理集中，但缓存、worker 和共享部署必须复核权限 | 有条件；需确保供应商调用前由本系统过滤，且供应商范围与本地授权一致 | 有条件；可集中策略，也可能因服务间身份或策略传播不一致而泄露 |
| ASR-02 受控外发 | 较适合；默认不外发最直接，但云端问答可用性受限 | 较适合；云端适配器可被显式门控、替换或禁用 | 弱项；文档处理默认出域，与敏感文档和逐文件确认有张力 | 较适合；可建立独立模型网关，但需验证所有调用只能经网关 |
| ASR-03 证据与引用 | 较适合；原文与证据处在同一边界，仍须版本化和独立校验 | 较适合；证据契约贯穿处理、检索、生成和引用校验 | 有条件；要求供应商导出稳定来源元数据，否则难以复核引用 | 有条件；能明确拆分证据服务，但跨服务 ID、版本和一致性增加工作 |
| ASR-04 导入生命周期 | 有条件；进程内任务和崩溃恢复需设计，否则任务状态可能不完整 | 较适合；显式任务状态与 worker 边界便于区分解析/索引完成和失败 | 有条件；托管服务可能提供任务状态，但内部处理与重试可见度依赖供应商 | 较适合；异步处理自然，但最终一致性、重放和幂等需自行处理 |
| ASR-05 失败降级 | 较适合离线和无模型降级；单机资源或单进程故障影响面较大 | 较适合；保留本地检索路径，任务/模型失败可单独表达状态 | 弱项；网络或供应商故障可能同时影响处理、检索和问答 | 较适合故障隔离，但依赖数量增加也会带来更多不可用组合 |
| ASR-06 笔记锚点与导出 | 较适合；本地统一维护笔记和来源关系 | 较适合；统一业务核心可集中执行权限和引用检查 | 有条件；须保证笔记数据与外部处理结果有稳定版本映射 | 较适合但实现成本高；需协调笔记、权限和证据服务的一致性 |
| ASR-07 性能与容量 | 未知；适合小规模起步，缺少目标负载不能判断容量上限 | 可演进；可先同机部署，后续按测量拆 worker；仍需基准数据 | 潜在弹性较强；时延、成本、限流和数据规模均待供应商/负载验证 | 潜在独立扩展最强；当前没有负载证据支持其额外成本 |
| ASR-08 可修改性与替换 | 有条件；需以接口隔离解析器、检索器和模型，不应把替换等同拆服务 | 较适合；逻辑模块与适配器能独立演进，物理部署可暂时合并 | 弱项；供应商专有接口和数据格式可能形成绑定 | 较适合独立发布，但服务契约、兼容和集成测试负担最高 |
| ASR-09 可观测与恢复 | 有条件；状态可统一，但本机日志/备份和崩溃恢复需设计 | 较适合；阶段状态、任务错误和模型失败可显式追踪 | 有条件；外部处理的内部阶段可见度有限 | 较适合服务级观测，但需要集中日志、追踪和告警等运维能力 |

## 4. 方案权衡与筛选

### 4.1 候选 C 不作为默认方案

云端托管有潜在弹性和较少本地运维的优点，但当前并未验证云端解析/OCR对同批项目样本的质量，也未确认数据驻留、留存、成本和供应商服务边界。更重要的是，业务流程要求逐文件/版本确认、策略禁云时零调用，并要求证据能回到源版本。让原文处理默认出域会把最重要的隐私和证据风险交给尚未核实的外部边界。因此 C 不作为一期默认架构；未来可对公开或明确授权的文档重新评估。

### 4.2 候选 D 暂不作为起点

独立服务有利于隔离和按需扩展，但授权传播、版本一致性、跨服务失败与重试也会变成必须解决的问题。当前没有已确认的并发、规模、团队独立发布或可用性目标。把模块拆成多个进程不会自动提升权限安全、引用完整率或服务可用性。若未来实测显示解析/索引负载需要独立扩展，或不同团队需要独立发布，再从候选 B 的异步 worker/适配器边界演进。

### 4.3 候选 A 保留为部署剖面

候选 A 对单用户和离线演示最简单，并可作为候选 B 的“单机/无云”部署剖面；但它不应限制逻辑模块边界。若确认系统只需单机个人使用，且数据规模和任务时延可接受，可以把候选 A 作为最终物理部署，而不必部署独立 worker 或共享存储服务。

### 4.4 候选 B 的主要代价

- 相比纯单机方案，需要定义异步任务状态、重试/失败状态和阶段可观测性。
- 允许云端问答后，必须长期维护外发策略、证据白名单、模型适配器和引用核验；不能仅依赖模型提示词。
- 多人共享部署若被确认，还需要正式解决身份认证、撤权后的缓存复核、备份/恢复、审计和数据保留。
- 当前不选用特定数据库、向量库、队列或对象存储，也不承诺任何性能目标。

## 5. 首轮推荐

**推荐方向：以候选 B 作为逻辑架构基线，并保留候选 A 的单机部署剖面。**

建议先把系统组织为具有清晰业务边界的模块化单体：导入与版本管理、解析/索引任务编排、授权与策略、检索与证据、回答与引用校验、笔记与导出。解析/索引使用显式任务契约，但初期不要求引入独立消息中间件或独立部署集群。云端问答为可选适配器；默认流程仍能完成本地原文阅读、检索、证据展示和降级。

选择依据：

1. 符合当前最明确的安全、引用和降级不变量，且可以把权限过滤与证据契约放在核心业务控制路径中。
2. 解析和索引已有独立任务及状态要求，显式异步边界有助于表达“可阅读但不可检索”和处理失败；是否独立进程由后续负载测量决定。
3. 保持模块可替换，不把逻辑拆分误当成微服务部署要求。
4. 能从单机演示开始，也能在协作规模和性能目标明确后增加 worker 或外部存储。
5. 现有实验验证的是特定权限、门控和降级契约，而不是生产规模。因此推荐结构先解决证据与治理链路，不以未经验证的扩展能力为选型理由。

这是一项**首轮架构建议**，不是已获组内批准的最终决策。若组内确认仅需单用户离线使用，或反而确认高并发共享部署及明确 SLA，应重新评估 A/B/D 的部署取舍。

## 6. 后续 ADR 与未决输入

首轮决策详见 [ADR-001：模块化单体与受控异步处理](ADR-001-智能笔记助手模块化单体与受控异步处理.md)。ADR 记录逻辑架构建议，并将部署规模、worker 是否独立进程、持久化技术和云端模型供应商标为未决，不用一个架构风格选择替代这些需求确认。

进入项目架构视图前，建议组内至少确认：

| 输入 | 当前状态 | 对选型的影响 |
|---|---|---|
| 主要使用方式 | 单用户本地、单机演示或多人共享，尚未定 | 决定是否需要集中式身份、共享数据存储和 worker 部署 |
| 运行位置与系统资源 | 本地设备、本地服务器或云端环境，尚未定 | 决定单机剖面是否可行及解析/索引如何部署 |
| 数据规模、并发和 P95 | 无批准数值 | 决定是否需要独立 worker、扩展策略和性能验证标准 |
| 外发与离线策略 | 流程已规定门控和逐文件/版本确认，敏感等级及默认值待定 | 决定云端适配器的默认开关和可用范围 |
| 保留、删除、备份与审计 | 运营边界未定 | 影响持久化、恢复、撤权传播和审计数据设计 |
