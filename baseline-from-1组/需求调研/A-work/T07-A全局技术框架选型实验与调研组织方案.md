# T07-A 全局技术框架选型实验与调研组织方案

## 文档定位

本文件回答三个问题：

1. 如果要为智能阅读器选择全局技术框架，最小可行实验应如何设计？
2. 本地优先、云端优先和混合部署是否都有可行性方案？
3. 全局架构实验与后续文档解析、OCR、检索、问答模型等局部调研有交叉时，如何组织顺序？

当前仍处于需求调研阶段。实验目的不是制作完整阅读器，也不是立即确定具体工具，而是识别架构边界、失败场景和一期范围约束。

## 一、先区分两个决策层次

### 1. 全局架构问题

全局实验要回答的是“系统怎样组织”:

- 文档是否需要统一中间表示；
- 解析、OCR、检索、模型和引用是否可以独立替换；
- 文档是否可以按敏感级别路由到本地或云端；
- 没有网络或模型不可用时能否降级；
- 引用能否从回答回溯到文档版本、页码、段落和原文；
- 一期所需的隐私、离线、性能和维护约束能否同时满足。

### 2. 局部技术问题

局部调研要回答的是“每个模块采用哪类实现”:

- 哪类解析器适合目标文档；
- 哪类 OCR 对样本的识别错误较少；
- 关键词、向量或混合检索的召回效果如何；
- 本地模型与云端模型在质量、时延、成本和隐私上如何取舍；
- 哪种引用定位方式在样本上最稳定。

**结论口径**：全局架构实验验证边界和连接方式，局部技术调研验证模块能力。两者可以共享样本和指标，但不能用局部模块的单项好成绩直接推出全局架构成立。

## 二、建议采用的全局实验方案

### 方案 A：黑盒路径对比

把候选系统当作黑盒，使用相同的样本和问题集，分别测试本地、云端和混合路径。

```text
相同样本 + 相同问题集 + 相同回答约束
       |             |             |
   本地路径       云端路径       混合路径
       |             |             |
       --------统一评价记录--------
```

**优点**：准备快，适合早期可行性筛查。  
**缺点**：无法准确区分解析、检索、模型和部署路径的影响；如果各路径使用不同工具，比较容易产生混杂变量。  
**适用阶段**：第一轮只用于发现明显不可行方案。

### 方案 B：适配器式最小链路实验（推荐）

先定义统一中间表示和模块接口，再用可替换适配器组成最小链路：

```text
样本导入
  -> 解析/OCR适配器
  -> CanonicalDocument
  -> 分块与来源映射
  -> 全文/向量/混合检索适配器
  -> 证据片段
  -> 本地/云端模型适配器
  -> 引用校验与降级控制
```

每次实验只替换一个模块或一条部署路径，并保存：

- 输入样本哈希和授权状态；
- 适配器名称、版本和参数；
- 中间表示、检索结果、模型输出和引用校验结果；
- 时延、资源、费用和失败原因。

**优点**：可以判断“模块可替换性”和“架构边界是否有效”，结果容易追溯。  
**缺点**：需要先写少量实验脚本和记录格式，但不需要制作产品原型。  
**适用阶段**：作为 T07-A/T07-B 的主实验方法。

### 方案 C：合成数据和故障注入实验

不上传真实资料，使用课程组自制或公开样本，主动注入网络中断、云端超时、空检索、低 OCR 置信度、模型拒答和索引过期等故障。

**优点**：适合验证隐私隔离、路由和降级。  
**缺点**：不能代替真实版面和真实服务质量测试。  
**适用阶段**：在方案 B 的链路稳定后执行。

## 三、要比较的全局候选路径

不要把路径名称写成最终选型，先比较以下三种配置：

| 配置 | 文档处理 | 索引与检索 | 问答 | 重点验证 |
|---|---|---|---|---|
| L：本地优先 | 本地解析/OCR | 本地全文和/或向量索引 | 本地模型；不可用时原文/检索降级 | 隐私、离线、资源占用、质量下限 |
| C：云端优先 | 云端解析/OCR 或外部服务 | 云端或托管索引 | 云端模型 | 质量上限、时延、费用、数据保留和服务限制 |
| H：混合路由 | 按敏感级别和网络状态分流 | 本地和云端可分开 | 敏感文档本地，普通文档可云端 | 路由正确性、隐私隔离、故障切换和维护复杂度 |

### 3.1 实验中应固定的变量

为了比较架构路径，以下变量应尽量固定：

- 样本和样本版本；
- 问题集和预期答案；
- 统一中间表示字段；
- 分块规则；
- `top_k`、上下文长度和回答格式；
- 引用校验规则；
- 评价指标和失败分类。

### 3.2 实验中可以变化的变量

- 本地、云端或混合部署路径；
- 解析/OCR/检索/模型适配器；
- 网络和服务状态；
- 文档敏感级别策略；
- 是否允许云端处理。

一次实验不应同时更换多个变量，否则只能观察到结果变化，不能解释变化原因。

## 四、最小实验内容

### EXP-ARCH-001：中间表示与来源链路

**目的**：验证解析结果是否能被统一表达，并能从检索片段回溯到原文。

**样本**：文本型 PDF、双栏 PDF、扫描 PDF、DOCX、Markdown/TXT、含表格或公式的文档。

**检查项**：

- 文档 ID、版本和页数；
- 块 ID、标题路径和顺序；
- 页码、坐标、字符偏移；
- 表格、图片、公式和脚注的保留方式；
- 解析器、OCR 版本和置信度；
- 原文 -> 块 -> 分块 -> 检索证据 -> 引用的映射。

**通过条件**：每个用于回答的证据片段都能定位回原文；无法解析的内容有警告而不是静默丢失。

### EXP-ARCH-002：三种部署路径对比

**目的**：比较 L、C、H 三种路径能否满足一期的硬约束。

**每条路径都执行**：导入、解析/OCR、索引、检索、回答、引用校验和失败降级。

**核心指标**：

- 解析成功率和目标段落召回率；
- 引用正确率和原文支持率；
- 无依据问题拒答率；
- 首次响应和完整回答的 P50/P95 时延；
- 单文档处理成本和资源占用；
- 网络不可用、模型不可用时的可用能力；
- 敏感文档是否发生未授权出域。

**注意**：云端路径只能使用公开或明确授权样本。未授权资料不能为了实验效果上传到云端。

### EXP-ARCH-003：模块替换实验

**目的**：验证解析器、OCR、检索器和模型是否可以独立替换。

**方法**：只替换一个适配器，比较：

- 是否仍能生成相同结构的中间表示；
- 是否需要重新解析、重新分块或重新索引；
- 引用位置是否仍然可回溯；
- 失败差异能否归因到被替换模块。

**通过条件**：模块替换不改变下游接口语义；变化可由版本、配置或能力差异解释。

### EXP-ARCH-004：故障与降级实验

注入以下故障：

- 网络中断；
- 云端服务超时或限流；
- 本地模型资源不足；
- OCR 置信度过低；
- 检索无结果；
- 证据与回答不匹配；
- 文档更新导致索引过期。

**最低可接受结果**：系统退回原文阅读、全文检索、证据展示或明确拒答；不能用无引用生成内容掩盖失败。

### EXP-ARCH-005：敏感文档路由实验

**目的**：验证敏感级别、授权状态和网络状态能否决定处理路径。

**测试矩阵**：

| 文档级别 | 网络 | 云端允许 | 预期路径 |
|---|---|---|---|
| 敏感 | 在线 | 否 | 本地处理 |
| 敏感 | 离线 | 否 | 本地处理或原文阅读 |
| 普通 | 在线 | 是 | 云端或混合路径 |
| 普通 | 离线 | 是 | 本地降级 |
| 未知 | 在线 | 未确认 | 不自动外传，先请求授权或走本地 |

## 五、实验记录和判定方式

每个结果使用唯一编号，例如 `TECH-ARCH-001-R01`。建议记录：

| 字段 | 内容 |
|---|---|
| 实验编号 | `TECH-ARCH-xxx-Rxx` |
| 架构路径 | L、C 或 H |
| 样本编号 | `DOC-xxx` |
| 问题编号 | `Q-xxx` |
| 模块版本 | 解析器、OCR、检索器、模型及适配器版本 |
| 配置 | 分块、`top_k`、上下文长度、提示约束等 |
| 预期结果 | 页码、段落、关键词、应拒答等 |
| 实际结果 | 原始输出和结构化评分 |
| 性能 | 处理时延、响应时延、资源占用 |
| 成本 | 本地资源估算或云端计费 |
| 失败原因 | 格式、布局、OCR、检索、模型、网络、权限等 |
| 结论 | 可行、受限、失败、待验证 |
| 降级方案 | 原文、全文检索、人工核验、拒答等 |
| 关联决策 | D03、D05-D09 |

建议采用四级判定，而不是简单的“成功/失败”：

- **可行**：达到预先定义的最低指标，且失败有可接受降级；
- **受限**：基础场景达到指标，但存在明确格式、隐私、成本或性能边界；
- **失败**：无法支持核心场景，或违反硬约束；
- **待验证**：样本、资料或实验不足，不能做判断。

## 六、全局实验与局部调研的交叉边界

### 6.1 会交叉的内容

以下内容会同时出现在全局实验和局部调研中：

- 本地/云端模型的质量、时延、成本和隐私；
- OCR 或解析结果对检索和引用的影响；
- 检索召回对问答质量的影响；
- 服务不可用时的降级路径；
- 多文档权限和数据出域控制。

### 6.2 不应混为一谈的内容

| 内容 | 属于全局架构实验 | 属于局部技术调研 |
|---|---|---|
| 本地与云端路径是否能被路由和降级 | 是 | 否，局部只提供能力数据 |
| 某个模型回答质量是否更高 | 只做路径级结果观察 | 是，重点评测模型能力 |
| 统一 IR 能否承接不同解析器 | 是 | 解析调研提供输出证据 |
| 某 OCR 引擎 CER 是否更低 | 仅作为架构输入 | 是，重点比较 OCR |
| 混合部署是否违反敏感文档策略 | 是 | 云服务条款和模型数据政策提供事实 |
| 具体向量库性能 | 否，除非影响架构边界 | 检索调研范围 |

### 6.3 处理重合内容的规则

对同一问题设置两个层级的记录：

1. **局部事实记录**：例如某模型在固定问题集上的引用正确率、时延和成本。
2. **架构使用记录**：例如在 H 路径中，这个模型是否能被替换、是否允许处理某类文档、失效后能否降级。

局部实验的结果可以成为架构实验的输入，但架构结论必须额外考虑接口、权限、故障和运维条件。

## 七、推荐的组织顺序

### 阶段 0：先确定硬约束，不选工具

明确：

- 一期支持哪些格式；
- 是否要求离线阅读/检索；
- 哪些文档禁止外部处理；
- 引用最低粒度；
- 无依据问题是否必须拒答；
- 可接受的时延、成本和资源上限。

这些是架构实验的输入，不应由某个工具的宣传能力反向决定。

### 阶段 1：先定义统一中间表示、接口和评价集

在比较模型之前，先固定：

- `CanonicalDocument` 的字段；
- `Chunk`、`Evidence` 和回答/引用记录；
- 样本编号、问题集和预期答案；
- 解析、检索、问答和引用指标；
- `TECH-xxx` 实验记录格式。

如果没有这一步，后续比较会混淆“工具输出格式不同”和“能力确实不同”。

### 阶段 2：做最小基线链路，不做完整产品

只完成：

```text
导入 -> 解析/OCR -> IR -> 分块 -> 全文检索
     -> 证据展示 -> 页码/段落定位
```

先证明文档和证据链可用，再加入生成模型。这样可以把解析/检索失败与模型失败分开。

### 阶段 3：做全局路径实验

使用同一套 IR、问题集和评价脚本，对 L、C、H 三种路径进行比较。此阶段的输出不是“选某个模型”，而是：

- 哪些路径违反隐私或离线硬约束；
- 哪些路径的质量、成本和时延进入可接受区间；
- 需要哪些降级能力；
- 哪些模块必须保持独立。

### 阶段 4：并行开展局部技术调研

全局实验确定接口和约束后，再开展：

1. 文档解析与 OCR；
2. 结构识别和引用定位；
3. 全文、向量和混合检索；
4. 本地与云端模型；
5. 多文档和权限过滤。

局部调研应复用同一批样本、问题集和指标，但可以增加各自的专门指标。

### 阶段 5：回填全局实验并做二次确认

用局部调研中表现较好的候选实现替换基线适配器，重新执行：

- 三种路径对比；
- 故障注入；
- 引用链路；
- 敏感文档路由；
- 成本和性能测量。

只有这一轮完成后，才适合形成“候选架构受限可行”或“某路径不适合一期”的建议。

## 八、本地模型与云端模型调研应如何放置

### 8.1 不建议最先比较模型

如果解析、分块、检索和引用尚未固定，模型回答差异无法解释：

- 可能是检索没有召回证据；
- 可能是 OCR 文本已经错误；
- 可能是上下文过长或分块不合理；
- 可能是引用校验规则不同；
- 也可能确实是模型能力不同。

因此，模型调研不应作为全局实验的第一步。

### 8.2 也不应等所有局部调研结束才开始

模型的隐私政策、上下文限制、调用成本、离线资源需求和响应时延，会反过来影响架构是否可行。因此在阶段 3 可以做一轮**早期模型筛查**，只回答：

- 是否满足数据出域限制；
- 是否能处理最小证据上下文；
- 是否存在明显不可接受的时延或成本；
- 是否支持回答约束和拒答格式。

此时不要把筛查结果写成最终模型选型。

### 8.3 推荐的模型调研顺序

1. **资料调研**：数据保留、训练使用、区域、配额、上下文限制、版本策略和价格。
2. **最小能力筛查**：固定证据片段和固定问题集，比较支持率、拒答率、引用格式和时延。
3. **局部深入实验**：在稳定的解析/检索链路上比较事实正确性、跨段推理、多文档冲突和成本。
4. **回填全局路径**：把通过局部筛查的模型放入 L/C/H 路径，验证权限、故障和降级。

## 九、推荐的交付物拆分

### T07-A：全局架构与实验设计

- 架构候选 L/C/H；
- 数据流和模块边界；
- 统一 IR 和接口；
- 硬约束、指标和判定规则；
- 实验矩阵和数据合规规则；
- 尚未解决的问题。

### T07-B：最小链路和架构实验记录

- `TECH-ARCH-xxx` 原始记录；
- 本地/云端/混合路径运行结果；
- 故障注入和降级结果；
- 引用链路和敏感文档路由结果。

### 后续局部调研

- `TECH-DOC-xxx`：文档解析、OCR、结构识别；
- `TECH-RET-xxx`：全文、向量、混合检索；
- `TECH-MOD-xxx`：本地和云端模型；
- `TECH-CIT-xxx`：引用定位和支持率；
- `TECH-MULTI-xxx`：多文档、权限和冲突处理。

局部编号与架构编号分开，但必须通过样本、问题集和 `CanonicalDocument` 关联。

## 十、当前建议与暂不应做的结论

### 当前建议

1. 采用“统一 IR + 适配器 + 固定评价集”的实验框架。
2. 先用最小基线链路验证证据和引用，再加入问答模型。
3. 先做 L/C/H 路径的硬约束筛查，再做局部组件优化。
4. 本地与云端模型调研提前做隐私、配额和成本筛查，深入质量评测放在检索链路稳定后。
5. 让局部调研复用架构实验的样本、问题集和记录口径，但保留局部专用指标。
6. 通过第二轮回填实验确认“局部最佳组件”是否真的适合整体架构。

### 暂不应做的结论

- 不应因为某个云端模型单项回答质量高，就直接决定云端优先；
- 不应因为某个本地模型可离线运行，就直接决定本地优先；
- 不应因为混合路径理论上灵活，就直接认定其维护成本可接受；
- 不应把不同解析器、检索器和模型同时更换后的结果，解释成单一模块优势；
- 不应在没有引用链路和故障实验的情况下，宣布问答链路“可用”；
- 不应在真实样本、授权状态和服务条款未明确前，把云端实验结果外推到敏感文档。

## 十一、最小决策输出模板

完成第一轮实验后，建议只输出以下形式：

> **原始事实**：在 `TECH-ARCH-xxx` 中，路径 H 在授权普通文档上达到某指标；在敏感文档和离线场景下自动切换到路径 L；某类双栏样本引用定位失败。  
> **项目组解释**：混合路径可以满足普通文档的质量目标，但依赖稳定的路由和本地降级；双栏文档仍是解析和引用风险。  
> **技术/需求建议**：一期可考虑“普通文档允许云端、敏感文档本地”的候选约束；双栏文档列为有限支持，等待局部解析实验继续验证。  
> **尚未解决**：模型质量、成本、服务条款和复杂版面覆盖率仍需局部实验和第二轮集成确认。
