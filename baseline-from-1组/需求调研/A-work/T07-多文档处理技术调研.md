# T07 多文档处理技术调研

## 文档定位

本报告是 T07 的第七个技术环节，研究“多文档导入、组织、检索和问答”是否适合进入一期。它不把某个向量数据库、模型或云服务写成最终选型，而是把已有单文档链路扩展到多文档时新增的需求、权限、质量、性能和合规约束分开记录。

证据口径沿用本项目其他 T07 报告：

- **原始事实**：已有实验、官方文档/标准、论文或可复现实验直接支持的内容。
- **项目解释**：把事实映射到智能阅读器。
- **建议**：可用于一期范围和下一轮原型设计的条件式建议。
- **待验证**：没有被当前实验覆盖，不能写成已实现能力。

本报告读取并复用的上游材料包括：`T07-A智能阅读器全局技术框架调研.md`、`T07-文档检索技术调研.md`、`T07-文档问答技术调研.md`、`T07-回答引用和原文定位技术调研.md`，以及 `TECH-RET-008-R01`、`TECH-RET-009-R01`、`TECH-RET-010-R01`、`TECH-CIT-007-R01`、`TECH-QA-001-R01`。已有多文档结果是受控小样本验证，不等于生产级权限或规模结论。

## 1. 先区分四类能力

“支持多文档”不是一个单一开关，四类能力的风险和一期价值不同。

| 能力 | 定义 | 一期判断 |
|---|---|---|
| 1. 同一用户在多份授权文档中搜索 | 用户在明确选择的文档集合/知识库中检索，结果仍按文档和版本显示 | **建议支持**。这是多文档的最低价值能力，能复用全文/BM25和现有证据定位。 |
| 2. 多份文档联合回答 | 回答需要综合两份或以上授权文档，并逐条绑定来源、版本和原文证据 | **有限支持**。只做有证据覆盖、来源可区分、无冲突或可显式呈现冲突的比较/汇总。 |
| 3. 不同用户或不同权限文档之间的隔离 | 权限、租户、项目、保密级别决定文档是否进入检索、上下文、缓存、日志和回答 | **必须支持为基础安全能力**。不是可选增强；权限过滤必须在检索排序和模型调用之前完成。 |
| 4. 跨知识库或跨项目问答 | 一个问题跨越不同知识库、项目或组织边界，通常还涉及不同策略和责任人 | **一期暂不支持**。除非明确建立统一授权、审计、保密和冲突策略，否则只允许用户先把文档复制到同一授权集合。 |

结论：一期可以交付“同一用户、同一授权范围内的多文档搜索”，并对联合回答提供受限能力；不能把“所有用户、所有项目、所有保密等级的全局问答”作为一期承诺。

## 2. 需求价值与新增复杂度

### 2.1 价值场景

多文档能力的价值主要出现在：

1. **课程/研究资料汇总**：在同一课程讲义、论文和实验报告中找共同概念。
2. **版本比较**：比较规范、方案或报告的修订差异，必须显示版本和更新时间。
3. **证据交叉核验**：同一问题需要多个来源，回答要说明一致、互补或冲突。
4. **专题资料检索**：用户不想逐份打开文档，而是在授权资料集内先定位候选段落。

### 2.2 不应把多文档当作单文档的线性放大

多文档新增了至少六个状态维度：

- 结果属于哪份文档、哪个版本、哪个来源和更新时间；
- 用户在本次查询时是否仍有权访问该文档；
- 不同文档是否在说同一件事，结论是否冲突；
- 多个相似块是否造成检索噪声和来源偏置；
- 证据总量是否超过模型上下文或本地资源预算；
- 某份文档更新/删除后，旧索引、缓存和回答引用是否仍有效。

因此多文档问答的最小闭环应是：

```text
选择文档范围
 -> 读取当前授权快照和保密策略
 -> 只在允许范围内检索
 -> 按文档/版本去重、重排和分组
 -> 检查证据覆盖、冲突、置信度和上下文预算
 -> 生成带来源矩阵的回答或拒答/人工复核
```

## 4. 多文档数据模型和组织方式

### 4.1 组织层级

一期建议至少区分四层对象，而不是把所有块直接塞入一个全局索引：

```text
用户/租户
  -> KnowledgeBase（知识库或项目）
      -> DocumentSet（用户本次选择的文档集合）
          -> Document（逻辑文档）
              -> DocumentVersion（不可变版本）
                  -> Block/Chunk（可引用索引单元）
```

- `KnowledgeBase` 是权限、保密策略和索引生命周期的主要边界。
- `DocumentSet` 是一次查询的显式范围；默认不扩大到用户所有文档。
- `Document` 表示同一逻辑材料；文件重传或更新产生新 `DocumentVersion`。
- `Block/Chunk` 必须沿用现有 IR 的 `block_id`、页码/章节、字符偏移、源哈希和解析版本。

### 4.2 最低元数据契约

```text
Document
- tenant_id / owner_id / knowledge_base_id
- document_id                 # 逻辑稳定 ID
- title / original_filename
- source_type / source_uri_or_label
- sensitivity_class
- acl_version / allowed_principal_or_group
- created_at / updated_at
- current_version_id

DocumentVersion
- document_version_id
- source_hash / source_system / source_locator
- version_label / effective_at / ingested_at
- parser_version / chunking_version
- index_version_fulltext / index_version_vector
- page_count / language
- status: processing | ready | stale | deleted | failed

Chunk/Evidence
- document_id / document_version_id / block_id
- section_path / physical_page / printed_page_label
- char_start / char_end / quote / bbox
- sensitivity_class / acl_snapshot_id
- retrieval_method / score / rank
- confidence / provenance
```

`title` 和文件名不能作为主键；同名文件、复制文件、不同版本必须通过 ID、哈希和来源区分。更新时间必须同时保存“源文档声明的生效时间”和“系统导入时间”，因为两者可能不同。

### 4.3 导入和组织建议

1. 导入时先登记元数据和授权状态，再进入解析队列；未通过授权的文件不进入索引。
2. 支持批量导入，但每个文件都产生独立处理状态、错误原因和版本记录。
3. 用户可建立“课程/项目/专题”集合；查询默认只在当前集合内，避免全局召回噪声。
4. 同一来源重新导入时用源哈希去重；内容变化则创建新版本，不能覆盖旧版本的引用对象。
5. 结果、引用和审计日志都保留 `document_id + document_version_id`，不能只显示标题。

## 5. 单文档与多文档方案比较

| 维度 | 单文档方案 | 同一知识库多文档方案 | 跨知识库/跨项目方案 |
|---|---|---|---|
| 用户价值 | 解释段落、定位原文、单篇摘要 | 专题搜索、比较、综合证据 | 组织级知识问答、跨项目复用 |
| 权限 | 文档级即可 | 查询时需集合/文档级 ACL 过滤 | 需跨租户策略、委托和统一审计 |
| 检索 | 结果较少，噪声可控 | 需要去重、每文档配额和来源平衡 | 需要联邦检索和策略合并 |
| 回答 | 证据链较短 | 需区分来源、版本和冲突 | 还需处理策略不一致和责任边界 |
| 上下文/成本 | 较低且稳定 | 随文档数和证据扩展 | 最难预测，容易超预算 |
| 索引更新 | 单文档重建简单 | 增量 upsert、删除和版本并存 | 多库一致性和跨服务同步 |
| 隔离风险 | 低到中 | 中到高，尤其缓存和错误文案 | 高，存在权限侧信道和跨项目泄露 |
| 一期定位 | 已有基础 | **建议支持搜索，联合回答有限支持** | **暂不支持** |

推荐以“单文档能力为基线、同一知识库多文档为增量层、跨知识库为后续项目”推进。多文档层不能绕过单文档解析、引用和拒答门。

## 6. 跨文档检索和回答设计

### 6.1 跨文档检索

推荐顺序：

1. 固定本次 `DocumentSet` 和授权快照。
2. 在检索器入口做 ACL、租户、知识库和保密等级过滤。
3. 关键词/BM25 和向量检索分别召回，记录检索方法和索引版本。
4. 在文档内做父块/邻接扩展，在文档间做去重和来源配额。
5. 采用“每文档至少保留一个候选、全局按证据质量排序”的策略，避免某一篇长文档淹没其他来源。
6. 进行版本、更新时间、置信度、冲突和上下文预算检查后再生成。

现有 `TECH-RET-008-R01` 已验证“先过滤再排序”在受控样本中未发生未授权泄露；现有 `TECH-RET-009-R01` 已显示词面命中不代表有答案。因此多文档检索不能只按相似度取全局 top-k。

### 6.2 跨文档回答

回答器输入必须带文档边界和来源矩阵，例如：

```text
[DOC A | v2 | updated=... | source=...]
evidence A1 ...
[DOC B | v1 | updated=... | source=...]
evidence B1 ...
```

输出要求：

- 每个事实 claim 绑定一个或多个 `citation_id`，由服务端映射真实文档/版本/位置；模型不能自由生成页码。
- 先回答“各文档分别说什么”，再回答“可否综合”；不要把不同条件下的结论拼成一个新事实。
- 同结论可合并，但保留所有支撑来源；不同版本必须说明时间和版本。
- 冲突不能静默投票。输出 `needs_human_review` 或并列差异，除非有明确的时效/权威等级策略且可审计。
- 权限过滤后的空集必须回答“在当前授权范围内未找到依据”，不能暗示还存在不可见材料。

### 6.3 冲突、混淆和噪声风险

| 风险 | 典型原因 | 必须观察的症状 | 控制措施 |
|---|---|---|---|
| 结论冲突 | 不同版本、口径或有效日期 | 回答给出单一值但引用了相反来源 | 按版本/日期分组、并列差异、转人工；记录冲突字段。 |
| 引用混淆 | 同名文件、相同标题、模型自由生成页码 | 引用文档名正确但页/段落错 | 使用 ID/版本/哈希和 citation allow-list；服务端二次校验。 |
| 检索噪声 | 重复文件、长文档块过多、页眉页脚、主题相似 | top-k 被一篇长文档占满，或无答案题也有命中 | 每文档配额、去重、字段降权、无答案证据门。 |
| 条件丢失 | 文档只在特定时间、角色或范围内成立 | 综合回答删除限定词 | 保留上下文窗口和条件字段；claim 级支持检查。 |
| 版本漂移 | 索引旧、回答缓存旧、文档删除未传播 | 点击引用跳到新文或已删除文档 | 版本绑定、stale 标记、删除 tombstone 和缓存失效。 |
| 权限侧信道 | 结果计数、错误、耗时、缓存暴露隐藏文档 | 用户能推断文档存在或标题 | 过滤前置、统一空结果文案、审计日志脱敏、缓存按 ACL 隔离。 |
| 文档提示注入 | 文档中出现“忽略规则/泄露其他文档”等文本 | 模型改变系统策略或跨权限取证 | 文档内容只作不可信数据；系统规则和证据门在模型外。 |

已有 `TECH-CIT-007-R01` 已观察到允许来源 2 个、过滤来源 1 个、冲突状态为 `needs_human_review`；该结果只证明状态机探针，不证明真实模型能稳定识别所有语义冲突。

## 7. 文档数量、页数和上下文限制

### 7.1 限制应分为三层

1. **导入限制**：单文件大小、页数、解析超时、批量并发。
2. **索引规模限制**：知识库文档数、总页数、块数、向量维度和磁盘/内存。
3. **查询限制**：本次可选文档数、候选块数、上下文 token、回答时间。

不能用“模型上下文窗口”代替前两层；全文送入模型也会放大成本、噪声和长上下文退化。

### 7.2 一期建议的起始门槛（候选值，必须实测）

| 项目 | 建议起始值 | 说明 |
|---|---:|---|
| 单次查询文档数 | 20 份 | 超过则要求用户缩小集合或先做章节/文档级粗检索。 |
| 单次查询总页数 | 2,000 页 | 只作为检索范围门槛，不把 2,000 页直接放进上下文。 |
| 每文档候选证据 | 1 至 3 个块 | 防止长文档占满 top-k；冲突问题可临时扩展。 |
| 全局证据块 | 8 至 16 个 | 需按问题类型和证据覆盖率调节。 |
| 目标上下文 | 4k 至 8k tokens | 适合一期稳定性实验；保留来源和引用元数据。 |
| 硬上下文上限 | 16k tokens | 超过则分阶段摘要/比较或拒答，不盲目截断。 |
| 知识库规模 | 100 份/10,000 页起步 | 这是本地原型的压力测试档位，不是生产承诺。 |

这些数值是产品原型的**候选初始值**，不是模型或硬件保证。必须通过 `TECH-MDOC-005` 的规模矩阵按本地设备、云端模型、文档类型和并发重新确定。若用户任务是全文比较，优先采用“每文档摘要 -> 证据回查”的分阶段链路，而不是无限增加上下文。

## 8. 索引更新、版本和删除

### 8.1 更新

- 文档内容不可变版本化：新内容生成新的 `document_version_id`、源哈希、解析/分块版本和索引版本。
- 更新流程采用 `processing -> ready` 状态；新版本未就绪前，旧版本是否继续可检索必须由策略明确。
- 全文和向量索引独立记录版本；向量模型或分块规则变化时不能混用旧向量空间。
- 采用增量 upsert；失败时保留旧版本并标记新版本 `failed`，不能出现“元数据已更新但证据不可回溯”。

### 8.2 删除

- 删除先写授权不可见的 tombstone，再异步清理全文、向量、缓存、临时文件、导出物和云端副本。
- 删除确认应按 `document_id + version_id + index_version` 检查；不能只从 UI 列表消失。
- 删除中的文档不得继续进入新查询；正在运行的回答要在提交前重新检查版本和 ACL。
- 需要记录删除请求时间、完成时间、残留检查结果和失败重试，不把“调用删除 API 成功”当作物理删除证明。

### 8.3 一致性风险

最危险的窗口是：文档已被撤权/删除，但某个向量索引、查询缓存、回答缓存或云端任务仍可返回其片段。验证必须覆盖并发查询、更新中查询、删除后旧链接、重试和服务重启，而不是只测单线程 happy path。

## 9. 不同保密等级能否混合检索

### 9.1 推荐的一期政策：默认不混合

建议至少设置 `public / internal / confidential / restricted` 四级（实际名称由组织规则确定），并执行：

1. **默认拒绝跨等级混合检索**，尤其禁止 restricted 与其他等级进入同一云端上下文。
2. 同一用户即使同时有权限，也先按保密等级分路由、分索引或分 namespace；只有策略明确允许时才做本地受控合并。
3. 回答输出的敏感级别不低于最高敏感证据；不得把 restricted 事实降级到 public 笔记、日志或云端提示词。
4. 云端路径只接收明确允许出域的文档；敏感文档默认本地解析、索引和证据模式。
5. 不能把“用户有权限”与“允许送入第三方模型”混为一谈：授权范围、保密策略和外部处理同意是三个条件。

### 9.2 何时可以有限混合

可在后续实验中验证“同一用户、同一知识库、本地执行、统一输出策略”的混合检索，但必须有：最高等级策略、结果和日志分级、导出防护、人工审计和删除验证。跨项目、跨租户或任何需要将高等级片段发送至云端的混合检索，一期不支持。

## 10. 本地与云端方案对多文档处理的影响

| 维度 | 本地多文档 | 云端多文档 | 混合/策略路由 |
|---|---|---|---|
| 数据边界 | 文档、索引和上下文可不出设备，但要检查本机日志/备份 | 片段、查询、元数据可能出域，受合同、区域和保留政策约束 | 可按等级和任务分路由 |
| 规模弹性 | 受 CPU/GPU、磁盘、内存和并发影响；索引规模易成为瓶颈 | 易扩容，但有配额、限流、网络和供应商依赖 | 需要双路径和一致性策略 |
| 更新/删除 | 可直接控制索引和缓存，验证相对明确 | 需验证服务端索引删除、缓存、日志和备份保留 | 删除链路最长、审计复杂度最高 |
| 跨文档质量 | 本地模型上下文/吞吐可能限制联合回答 | 更容易使用大上下文模型，但不代表冲突处理正确 | 普通文档可云端，敏感文档本地 |
| 成本 | 主要是设备、存储、电力和维护成本 | 按输入/输出 token、检索存储、向量库、网络和重试计费 | 两类成本并存 |
| 失败模式 | 资源耗尽、模型不可用、设备离线 | 网络、429/5xx、政策变化、出域失败 | 路由错误、结果不一致、重复索引 |
| 一期定位 | 敏感/离线首选，至少保留本地检索和原文浏览 | 公开或明确授权资料的候选加速路径 | 作为后续验证目标，不直接承诺全量混合 |

多文档会放大云端成本：输入 token 随证据数增加，冲突/重试会再次调用模型，且查询改写、重排和分阶段摘要可能产生多次调用。成本评估必须记录输入/输出 token、检索块数、重排次数、调用次数、失败重试和存储/网络费用，不能只记录“每次问答价格”。

## 11. 多文档最小实验设计

### 11.1 样本构成

在现有项目自制样本和已授权样本基础上，新增一个小型、可脱敏的多文档集：

| 类别 | 数量建议 | 目的 |
|---|---:|---|
| 同主题且结论一致 | 3 份 | 测试来源覆盖、去重和联合回答。 |
| 同主题且结论冲突 | 2 份 | 测试版本/日期/口径区分和人工复核。 |
| 同一逻辑文档的 v1/v2 | 2 个版本 | 测试版本更新、旧引用和 stale。 |
| 不同保密等级 | 3 份 | 测试默认拒绝混合、允许集合和出域路由。 |
| 不同用户/项目 | 3 份 | 测试租户/项目隔离和存在性不泄露。 |
| 同名或近重复文档 | 2 份 | 测试来源混淆和去重。 |

每份文档记录授权证明、来源、版本、更新时间、敏感级别、页数、语言、解析状态和预期金标准。优先使用项目自制或公开授权材料，不将真实敏感文件上传云端。

### 11.2 问题集

至少包含：

- 单一事实只在一份文档中出现；
- 同义表达需要跨文档检索；
- 两份文档共同支撑一个结论；
- 一致结论的合并摘要；
- 不同版本的“当前/历史”比较；
- 明确冲突的数值、日期和条件；
- 无答案但存在相似词；
- 仅在未授权文档中出现答案；
- 同名文档的来源辨识；
- 删除/撤权后旧缓存和旧引用；
- 不同保密等级的混合查询；
- 文档中包含提示注入文本。

### 11.3 实验步骤和对照组

1. 先建立单文档基线：相同问题只给目标文档。
2. 逐步增加文档数和总页数，比较全局 top-k、每文档配额和分阶段汇总三种策略。
3. 对每个问题固定授权快照，分别执行允许集合、过滤集合、撤权集合。
4. 对冲突和版本题记录模型前的证据矩阵，再评估回答是否正确区分来源。
5. 变更、重解析、删除和恢复索引，在每个阶段重新查询并检查 stale/不可见状态。
6. 同一证据包分别走本地证据门、本地模型和云端模型；云端只用公开或明确授权样本。
7. 测试上下文 2k/4k/8k/16k token 档位，并把证据放在开头、中间、末尾观察位置退化。

### 11.4 记录指标

质量：

- `Recall@k`、MRR/nDCG、跨文档证据全覆盖率；
- 文档/版本来源区分正确率；
- claim support rate、citation precision、冲突保留率；
- 无答案正确拒答率；
- 未授权文档泄露率和存在性泄露率，目标均为 0；
- 版本更新后旧引用 stale 检测率、删除后不可见率。

性能/资源：

- 导入和解析时间、索引构建时间、增量更新时间；
- 检索 P50/P95、重排时间、首 token 和完整回答时间；
- CPU/GPU/内存/磁盘、索引大小、缓存命中率；
- 并发 1/4/8/16 下的吞吐、排队和失败率；
- 输入/输出 token、模型调用次数、重试次数、每文档和每次问答成本。

### 11.5 通过/不通过原则

- 权限过滤、缓存、日志和错误路径不得出现未授权文档内容或存在性；
- 任何引用必须绑定正确文档、版本和证据位置；
- 冲突不得被压成无来源单一结论；
- 删除/撤权后的新查询必须不可见，旧回答必须可审计并标 stale；
- 扩大文档数量只能在质量、时延和上下文预算都仍可接受时放宽限制。

## 12. 权限和数据隔离验证项

建议至少执行以下验证矩阵：

| 验证项 | 检查点 | 失败判定 |
|---|---|---|
| 查询前 ACL | filter 是否在全文/向量召回前执行 | 未授权 chunk 进入任意候选集 |
| 多租户隔离 | tenant/project/knowledge_base 条件是否同时生效 | 只靠前端传 document_id 或可跨租户命中 |
| 文档存在性 | 空结果、计数、排序、错误码、耗时是否暴露隐藏文档 | 用户能确认标题、页数或“有/无该文档” |
| 结果/回答 | citation、来源矩阵、摘要和拒答文案 | 隐藏文档 ID、标题、摘要或相似片段出现 |
| 缓存 | 查询缓存、向量缓存、回答缓存是否绑定 ACL 快照 | 授权变化后复用旧结果 |
| 日志/监控 | debug、trace、错误和指标标签是否脱敏 | 原文或高敏元数据写入普通日志 |
| 索引物理隔离 | namespace/collection/partition/filter 是否按策略配置 | 仅逻辑 UI 隔离、底层可任意扫描 |
| 撤权/删除 | 撤权立即不可见，删除最终清理索引/缓存/备份 | 旧索引或缓存仍返回内容 |
| 外部调用 | 云端请求只含允许出域片段和必要元数据 | 敏感文档或未授权字段出域 |
| 混合保密 | 最高等级、输出、导出和日志规则是否执行 | 高敏内容被降级或混入低等级知识库 |
| 提示注入 | 文档指令不能改变 ACL、系统规则或工具权限 | 文档内容获得指令优先级 |

`TECH-RET-008-R01` 的“未授权泄露率 0”只能覆盖其受控样例和实现；生产验收必须把以上缓存、日志、删除和侧信道项加入黑盒及白盒测试。

## 13. 一期范围建议

### 一期支持

- 同一用户在同一知识库/项目内选择多份已授权文档进行全文和混合检索；
- 文档级权限过滤、保密等级策略、来源/版本/更新时间显示；
- 多文档结果按文档分组，支持打开原文并核验引用；
- 对一致证据做有限联合回答，逐条 claim 绑定 citation；
- 冲突、版本不一致、低置信 OCR/表格和证据不足时拒答或转人工复核；
- 增量导入、版本化、撤权、删除 tombstone 和索引重建状态可见；
- 敏感文档默认本地检索/证据模式，云端仅处理明确允许的公开或普通文档。

### 有限支持

- 同一知识库内的跨文档比较、摘要和问答，限制查询文档数、总页数、候选块和上下文预算；
- 不同保密等级仅在本地、同一用户、明确策略和审计条件下实验性混合；
- 版本冲突可以展示差异和时间线，但不自动给“哪个一定正确”的结论；
- 云端多文档回答只使用脱敏/授权样本，必须记录传输范围、模型版本、token 和删除策略。

### 一期暂不支持

- 跨知识库、跨项目、跨租户的全局问答；
- 默认混合 `restricted` 与其他等级，或将高敏证据发送到未批准云端服务；
- 无来源的多文档综合结论、自动冲突裁决和跨文档事实写回；
- 以无限文档数、无限页数或“把全文塞入模型”为产品能力承诺；
- 没有 ACL/版本/删除审计的第三方托管知识库作为一期依赖。

## 15. 当前结论

1. **一期适合支持多文档检索，但范围应限定在同一用户、同一授权知识库/项目和显式选择的文档集合。**
2. **多文档联合回答只能有限支持。** 先做来源分组、证据覆盖和冲突检测；无法逐条引用、存在权限/版本/低置信度问题时拒答或转人工。
3. **权限隔离、版本/来源区分和删除可审计是多文档的前置条件，不是后续优化。** 现有 `TECH-RET-008-R01`、`TECH-CIT-007-R01` 支撑了接口方向，但还不足以证明生产隔离。
4. **不同保密等级默认不混合。** 允许例外也应先分路由、分索引、在本地完成并按最高等级处理输出；高敏文档不可因“用户有权限”就自动进入云端。
5. **本地路线适合敏感和离线多文档检索；云端路线适合公开/明确授权材料的弹性处理，但必须把出域、保留、删除、配额和成本纳入实验。** 混合路线值得验证，但复杂度最高，不应在一期承诺全量跨域联合问答。
6. **首轮离线实验已覆盖 `TECH-MDOC-001/002/003/006/007/008/009/010` 的基础链路；仍应完成 `TECH-MDOC-004/005/011/013`，再扩大一期的文档数、页数或联合回答范围。** 当前不能声称已验证无限规模、跨项目问答或云端敏感文档合规。

## 16. 首轮离线实验结果（TECH-MDOC-001-014-R01）

已运行 [`run_multidoc_experiment.py`](../../../experiments/retrieval-benchmark/run_multidoc_experiment.py)，结果见 [`TECH-MDOC-001-014-R01.md`](../../../experiments/retrieval-benchmark/results/TECH-MDOC-001-014-R01.md) 和对应 JSON。实验只使用项目自制合成文档，不调用生成模型、云端服务或真实敏感文件。

### 16.1 已验证结果

| 项目 | 结果 | 解释边界 |
|---|---:|---|
| 样本规模 | 12 份逻辑文档、43 个块、6 个问题 | 仍是最小受控 fixture，不代表真实文档规模。 |
| 元数据完整率 | 1.000 | 已覆盖文档、版本、哈希、来源、敏感级别和位置字段。 |
| 未授权泄露率 | 0.000 | 覆盖检索返回的黑盒结果；尚未覆盖缓存、日志和底层索引扫描。 |
| 授权问题平均证据覆盖 | 0.833 | 词面检索基线；不等于语义检索或模型回答正确率。 |
| 冲突处理 | 2 个来源均召回，状态应为 `needs_human_review` | 验证冲突保留和来源区分，不代表真实模型冲突识别质量。 |

| 保密等级 | 默认混合策略为 deny；public/restricted 可分别路由 | 只验证策略基线，不证明组织合规或云端删除。 |
| 噪声控制 | 每文档配额将长文档最多占 2 个候选块 | 需要在真实 BM25/向量/重排器上复测。 |
| 缓存/日志基础控制 | ACL 变化生成不同缓存键；审计事件不含原文 | 只验证契约逻辑，未连接真实缓存、日志或索引。 |
| 上下文预算 | 2k/4k/8k/16k token 估算档位可记账 | token 按字符估算，未验证模型长上下文质量。 |

规模记账档位已跑通 1/5/10/20/50/100 文档，候选上下文在全局最多 16 个证据块；Python fixture 的检索 p50/p95 为约 `0.0134/0.7526 ms`。该时延只能说明实验链路可运行，不能作为产品性能承诺。

## 17. 本地真实 embedding 对照结果（TECH-MDOC-005-011-R01）

已使用工作区缓存的 `BAAI/bge-small-zh-v1.5`，在 CPU、本地合成 fixture 上完成 BM25、真实向量和 BM25+真实向量 RRF 的多文档检索对照。运行器为 [`run_multidoc_real_embedding.py`](../../../experiments/retrieval-benchmark/run_multidoc_real_embedding.py)，结果见 [`TECH-MDOC-005-011-R01.md`](../../../experiments/retrieval-benchmark/results/TECH-MDOC-005-011-R01.md)。

| 方法 | 有答案平均证据覆盖 | 未授权泄露率 | 查询 p50/p95 |
|---|---:|---:|---:|
| BM25 | 1.000 | 0.000 | 10.493/11.871 ms |
| 真实向量 | 1.000 | 0.000 | 10.493/11.871 ms |
| BM25 + 真实向量 RRF | 1.000 | 0.000 | 10.493/11.871 ms |

规模记账档位为 1/5/10/20/50/100/500/1000 个块。当前 CPU 上，1000 个块的真实 embedding 批量编码约 `3372.526 ms`，BM25 查询约 `5.091 ms`；100 个块对应约 `384.749 ms` 和 `0.516 ms`，向量维度为 512。查询时延包含一次共享的问题 embedding 编码，不应理解为单独方法的完整生产 SLA。

本轮支持的判断：

- 权限过滤可以在 BM25、真实向量和混合融合之前执行，当前 fixture 未发生未授权泄露；
- 本地 embedding 索引的编码成本随块数增加，批量编码应作为导入/更新阶段成本单独记录；
- 一期保留 BM25、把真实向量作为可插拔增强的架构仍然可行。

本轮不能支持的判断：

- 不能证明跨文档生成回答正确、冲突识别正确或长上下文不退化；
- 不能用 43 个合成块推断真实论文/课程资料的召回质量；
- 不能替代本地模型吞吐、并发、云端价格、云端数据保留和删除验证。

因此 `TECH-MDOC-005` 已完成“本地小样本规模记账”的子项，但生产规模门槛仍未完成；`TECH-MDOC-011` 只完成本地检索子项，云端多文档质量/成本/合规对照仍未完成。

## 18. 官方 Codex CLI 多文档问答结果（TECH-MDOC-011-R06/R07）

按照问答模型实验已经验证的官方 Codex CLI/Responses 路径，使用每组 3 题、每组 60 秒超时、仅发送项目自制合成证据的配置完成多文档问答快速筛选。运行器为 [`run_multidoc_codex_cli.py`](../../../experiments/qa-benchmark/run_multidoc_codex_cli.py)，结果见 [`TECH-MDOC-011-R06.md`](../../../experiments/qa-benchmark/results/TECH-MDOC-011-R06.md) 和 [`TECH-MDOC-011-R07.md`](../../../experiments/qa-benchmark/results/TECH-MDOC-011-R07.md)。restricted 文档在云端证据包中被策略排除。

### 18.1 三模型首轮结果（R06）

| 模型 | 完成 | JSON 合法率 | 状态准确率 | 引用来自检索证据 | 拒答/复核准确率 | 批次 p50/p95 |
|---|---:|---:|---:|---:|---:|---:|
| `gpt-5.5` | 6/6 | 1.000 | 1.000 | 1.000 | 1.000 | 24.068/30.163 s |
| `gpt-5.6-sol` | 6/6 | 1.000 | 1.000 | 0.667 | 1.000 | 18.857/18.925 s |
| `gpt-5.6-luna` | 6/6 | 1.000 | 1.000 | 1.000 | 1.000 | 17.154/17.311 s |

R06 中 `gpt-5.6-sol` 的版本题和同名来源题把引用写成了带 `EVIDENCE` 前缀的字符串。虽然语义指向正确，但不满足严格 citation allow-list，说明多文档引用不能只检查“看起来指向正确”；必须校验 ID 字符串和服务端证据白名单。

### 18.2 引用约束复测（R07）

修正证据标记并明确要求只输出纯 `block_id` 后，`gpt-5.6-sol` 复测结果为：6/6 完成、JSON 合法率 `1.000`、状态准确率 `1.000`、引用来自检索证据 `1.000`、拒答/复核准确率 `1.000`。这只说明在当前合成题和提示下约束可通过，不能外推到所有问题或真实文档。

### 18.3 云端实验边界

- 该路径只测试结构化状态、来源区分和引用格式；没有做 claim-level 人工语义评分。
- 只发送项目自制合成证据，不能证明真实敏感文档的云端合规。
- 未计算成本；需要保存带日期的官方价格快照，再按输入/输出 token、重试和分组调用次数核算。
- 没有验证供应商索引删除、日志保留、区域、缓存和备份清理。

因此 `TECH-MDOC-011` 已完成“官方 CLI 路径下的合成多文档状态/引用快速筛选”，但真实业务质量、云端成本和数据治理验证仍未完成。
