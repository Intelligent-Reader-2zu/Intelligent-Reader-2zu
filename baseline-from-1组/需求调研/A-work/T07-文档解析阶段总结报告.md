## 1. 报告范围

本报告总结当前对文本型 PDF、扫描型 PDF、DOCX、Markdown 和纯文本的解析器调研，以及已完成的本地最小实验。当前项目尚无阅读器原型，也没有已经开发完成的文档解析、检索或问答链路。

本轮暂不进行 Azure、Google Cloud、AWS 或 Unstructured API 的云端实验，不上传项目样本。云服务只作为候选类别和后续可选分支记录。

## 3. 核心事实（F）

### 3.1 文本型 PDF

- `pdfplumber` 能读取物理页、文本字符/单词、bbox、线和矩形等对象；本轮 3 份文本型 PDF 均成功返回文本。
- `Docling` 能输出统一文档树、文本元素和表格对象；本轮 3 份文本型 PDF 均返回结构化输出。
- `Unstructured fast` 能输出带元素类型和页元数据的结果；本轮文本型 PDF 均成功返回文本元素。
- 三者均没有因为“成功返回文本”而自动证明阅读顺序、标题层级、段落边界或表格结构完全正确。

### 3.2 扫描型 PDF（本轮只做输入边界确认）

- `pdfplumber` 对 `SELF-004` 识别到物理页面和图片，但无文本层、未执行 OCR。
- `Unstructured fast` 对 `SELF-004` 只返回分页元素，无识别文本。
- `SELF-004` 在本轮 `TECH-DOC-007-R01` 仅被确认无文本层；没有启动 OCR，也不把它纳入正文、布局或结构评分。
- 历史候选实验中出现过 Docling OCR 输出和 Unstructured OCR 路径失败，但这些属于 OCR 调研环节，不作为本轮文本结构结论。

### 3.3 复杂布局

- `SELF-002` 双栏样本在 `Docling` 输出中出现列顺序、词间空格和表格单元格切分问题。
- `pdfplumber` 能取到文本和坐标，但本轮未完成基于人工标注的阅读顺序评分。
- `Unstructured fast` 能保留元素类型和页信息，但表格/复杂版式主要表现为线性文本元素。

### 3.4 DOCX、Markdown、TXT

- 既有本地基线证明 `python-docx` 可读取段落样式和表格，但不能直接提供可靠的最终视觉页码。
- Markdown 的 CommonMark 标题、段落和源行定位可以进入实验 IR；GFM 表格、脚注、数学公式等扩展必须独立固定方言和插件后验证。
- UTF-8 和 GB18030 TXT 已有显式编码回退基线；纯文本没有天然的标题、页码和布局语义。

## 4. 工程解释（I）

1. “文本字符可提取”与“自然阅读顺序正确”是不同指标。PDF 的字符通常按定位对象保存，双栏、浮动文本框、边注和脚注需要布局推断。
2. “有物理页码”与“能还原打印页码”是不同能力。PDF 可以保存物理页序，但封面、罗马数字和页码标签需要单独识别。
3. “识别到表格区域”与“恢复正确单元格结构”是不同能力。无边框表格、合并单元格、跨页表格和 OCR 表格必须分别评分。
4. OCR 结果必须与原图、页码、bbox 和低置信度信息共同保存。把 OCR 文本直接当作精确正文，会放大中文、英文混排、符号和公式错误。
5. DOCX 段落顺序和样式通常比视觉分页稳定；Markdown/TXT 的结构取决于语法、编码和项目方言，而不是解析器自动推断。
6. 对后续检索、问答和引用而言，原始输出和统一 IR 都需要保留；只保存扁平 Markdown 或纯文本会失去页码、坐标、层级和复核证据。

## 5. 阶段性技术结论（C）

### C-01：本地解析路线可行，但不存在单一候选覆盖所有格式和质量要求

当前证据支持本地运行 pdfplumber、Docling 和 Unstructured，并能够把结果保存为实验原始产物。它证明了“可以开展本地候选对比”，不证明某一候选已经达到生产质量。

### C-02：一期不应把扫描 PDF、复杂表格和公式问答列为无条件承诺

扫描 PDF 需要单独的 OCR 调研；本轮没有执行 OCR，因此不能对 OCR 准确率作判断。复杂表格和公式也没有足够指标支持“可靠结构化问答”结论。

### C-03：文本型单栏 PDF、DOCX、Markdown、TXT 更适合作为一期优先范围

这些格式更容易建立正文、标题/样式、行号或页级引用的可验证基线。该结论是范围优先级建议，不是对所有文件的成功保证；双栏、脚注、页眉页脚仍需明确降级。

### C-04：统一中间表示必须支持证据溯源字段

后续检索和问答至少需要保留：

```text
doc_id
source_hash
source_format
parser_name / parser_version / config_hash
element_id
element_type
text
physical_page
printed_page_label
bbox
char_start / char_end
heading_path
parent_element_id
confidence
asset_ref
```

现有 `DocumentBlock` 尚未覆盖这些字段。建议先在解析实验适配层验证字段，再决定是否扩展生产模型。

### C-05：Java 客户端首轮应隔离解析器实现

建议 Java 通过统一 `ParserAdapter -> ParseRunResult` 调用固定版本的 Python runner，或对 Apache Tika 建立独立 Java 原生对照。这样可以比较结果，而不把 Python 环境、模型缓存、进程超时和编码问题混入产品链路。

### C-06：当前没有足够证据做最终选型

本轮是 4 份 PDF 的冒烟测试，尚未完成人工标注级阅读顺序 F1、段落边界 F1、标题层级 F1、OCR CER/WER、表格单元格结构准确率、图片/公式召回率、引用 bbox 准确率、DOCX/Markdown 扩展对比和 Apache Tika 实验。因此目前只能形成范围与风险结论，不能宣布 Docling、pdfplumber 或 Unstructured 为最终方案。

## 7. 一期范围和降级建议

### 7.1 建议纳入一期基础支持

- UTF-8/GB18030 纯文本；
- Markdown，明确 CommonMark 基线和已启用扩展；
- DOCX 的正文、Heading 样式、基本表格和图片引用；
- 文本层存在的单栏 PDF，保留物理页码和文本块坐标；
- 解析失败、超时或结构不确定时，保留原文件并显示可解释的失败状态。

### 7.2 建议作为受限支持或实验能力

- 双栏 PDF：允许返回文本，但不承诺跨栏阅读顺序；必要时降级为页面级或分栏文本。
- 扫描 PDF：必须经过 OCR 质量阈值和人工抽样；低置信度内容保留原图和定位信息。
- 表格：一期可提供线性化文本和表格截图/坐标，不承诺所有合并单元格均可用于问答。
- 图片和公式：保留 bbox、图像或原始对象；不将缺失或错误 OCR 静默当作正文。
- DOCX 页码：优先使用标题路径、段落索引和字符偏移；稳定视觉页码需另行渲染验证。

### 7.3 明确降级规则

| 失败场景 | 建议降级 |
|---|---|
| 无文本层 PDF | 标记为需要 OCR；提供原页图和失败原因 |
| OCR 质量低 | OCR 文本 + 原图 + 低置信度标记，限制引用断言 |
| 双栏顺序不确定 | 页面级/分栏文本，禁止静默合并为自然顺序 |
| 表格结构失败 | 表格截图、线性化文本和坐标，不承诺单元格级问答 |
| 公式解析失败 | 保留公式区域图像或 bbox，不把 OCR 结果当精确公式 |
| 页眉页脚混入正文 | 保留元素类型，检索阶段降权而非直接删除 |
| DOCX 视觉分页不稳定 | 使用标题路径、段落序号和字符偏移引用 |
| 解析器运行失败 | 记录版本、配置、异常和输入哈希，进入人工或替代解析队列 |

## 8. 仍待验证的问题

1. 哪个候选在人工标注的双栏样本上具有更高阅读顺序和段落边界 F1？
2. Docling 扫描 OCR 的中文 CER、英文 WER、置信度和引用 bbox 准确率是多少？
3. Unstructured 的中文 hOCR 失败能否通过版本、Tesseract 输出格式或替代 OCR 后端修复？
4. 表格、合并单元格、跨页表格和公式在不同候选上的结构恢复准确率是多少？
5. Apache Tika 在 Java 原生部署下能否提供足够的页级/元数据字段，值得承担其运维优势？
6. DOCX 页眉页脚、脚注、图片关系和渲染页码是否满足引用需求？
7. Markdown GFM 表格、脚注、数学公式和代码块应固定哪些扩展和规范化规则？
8. 不同解析器的输出如何映射到统一 IR，同时避免丢失原始证据？
9. 本地 CPU 资源、模型缓存大小、批处理吞吐和超时阈值是否满足一期部署环境？

## 9. 下一轮实验建议（不含 OCR）

1. 为 `SELF-001` 至 `SELF-003` 补充人工参考标注和自动评分：正文字符召回、阅读顺序、标题层级、段落边界、页码/bbox 和表格结构；`SELF-004` 只记录无文本层，不计算 OCR 指标。
2. 在同一批文本型 PDF 上补跑 PyMuPDF `DICT/RAWDICT`，并将其与 pdfplumber、Docling 无 OCR输出和 Apache Tika 映射到统一 `ParseRunResult`。
3. 对 Docling 固定模型缓存、临时目录、OCR 关闭状态和配置哈希，复测双栏及表格样本；不把扫描样本纳入本轮结构评分。
4. 对 Apache Tika 的编码、页级元数据和线性化表格结果补充对照；特别记录 GB18030 受限结果。
5. 完成 DOCX、Markdown、TXT 的扩展样本和引用定位实验，固定 Markdown 方言和 TXT 编码策略。
6. 只有在上述非 OCR 指标和失败样本可比较后，才进入候选组合和最终选型讨论；OCR 另立调研环节。

### 9.1 当前轮次进展

`TECH-DOC-007-R02` 已完成 PyMuPDF `DICT/RAWDICT` 输出、固定证据检查和三份用户确认的人工结构标注。评分显示：三类解析器在自制文本层样本上的归一化字符召回均为 1.0；PyMuPDF 在双栏样本的严格段落边界召回为 0.2857；Docling 在两个单栏样本的非表格阅读顺序准确率为 0.6667、脚注召回为 0，并在新版双栏样本得到 0.7778 的表格单元格文本准确率；Tika 没有元素级页码、bbox、标题、脚注和表格网格。完整口径和结果见 `experiments/parser-benchmark/results/text-structure/TECH-DOC-007-R02-MANUAL-SCORE.md`。这些结果仍不足以做最终选型。

## 10. 结论摘要

> 本项目的本地文档解析技术路线是可行的，但解析质量取决于格式和版式，不能由单一工具或单一“文本抽取成功”指标代表。文本型单栏 PDF、DOCX、Markdown 和 TXT 适合作为一期优先范围；扫描 PDF、双栏顺序、复杂表格、图片和公式应采用受限支持、可见降级和独立质量指标。Docling 是当前值得继续验证的统一本地候选，pdfplumber/PyMuPDF 适合作为可解释的 PDF 低层对照，Unstructured 的 `fast` 可用于元素分类对照，但当前 Windows 中文 OCR 路径存在明确阻塞。最终选型仍需等待统一指标、更多样本和 Apache Tika/扩展格式实验结果。

本报告不改变现有产品模型、不引入云服务依赖，也不把任何候选工具标记为最终选型。
