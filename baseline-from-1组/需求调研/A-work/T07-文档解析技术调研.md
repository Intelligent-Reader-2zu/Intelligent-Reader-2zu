# T07 文档解析技术调研

> 项目：智能笔记助手——内置 AI 助手的智能阅读器  
> 阶段：需求调研与技术可行性验证  
> 调研范围：文本型 PDF、扫描型 PDF、Word、Markdown、纯文本
> 文档状态：候选方案与验证设计，不代表最终技术选型

## 0. 工作区现状校正

本调研对应的是需求调研和技术可行性验证阶段，当前工作区**没有阅读器产品原型，也没有已开发完成的 PDF、OCR、检索或问答产品链路**。

工作区已有的 `experiments/minimal-chain-java` 是一个明确限定范围的最小实验基线：

```text
Markdown/TXT -> CanonicalDocument -> 关键词检索
             -> Evidence -> MockModelAdapter -> 引用校验
```

该基线当前只验证以下事项：

- Markdown/TXT 的 UTF-8 读取、标题路径、行号和段落块映射；
- 统一中间表示的最小字段形态；
- 关键词检索、证据对象和 block ID 引用校验的可重复运行。

该基线**不能**证明文本型 PDF、扫描 PDF、DOCX、OCR、向量检索、本地模型或云端服务已经可行。当前基线结果 `TECH-ARCH-001-R01` 与本文件的解析器实验编号分开管理；后续解析器应通过适配器接入实验链路，但不得将实验代码或实验结果表述为产品能力。

当前 `DocumentBlock` 尚未包含 PDF 页码、打印页码、bbox、字符偏移、OCR 置信度、图片/公式/表格资产引用及解析器版本等字段。是否扩展现有模型，或建立解析实验专用 IR，应在 `TECH-DOC-012` 中通过样本实验决定。

## 证据标记

- **F（事实）**：可由资料直接追溯。
- **I（项目组解释）**：对事实的工程含义进行解释。
- **C（技术/需求结论）**：可用于范围、指标或降级决策。
- **R（待验证/风险）**：证据不足，必须通过项目样本实验确认。

## 1. 调研目标

确认不同文档解析方案在以下方面的可行性：

- 正文完整性与阅读顺序；
- 页码、标题、目录、段落边界；
- 双栏、脚注、页眉页脚、表格、图片、公式；
- 中文、英文、中英文混排；
- 本地部署与云端服务的部署、成本、隐私和版本稳定性；
- 解析结果是否能保留后续检索、问答和引用定位所需的证据链。

当前目标是建立候选方案和验证边界，不做最终选型。

## 2. 需要回答的技术问题

1. 文本型 PDF 的文本流是否完整，阅读顺序是否可靠？
2. 扫描 PDF 的 OCR 对中文、英文、混排、旋转和低清扫描是否可接受？
3. PDF 的物理页号、打印页码、页眉页脚能否区分？
4. PDF 标题是来自书签、字体推断、目录文本，还是布局模型预测？
5. DOCX 的段落样式、表格、页眉页脚、脚注和分页信息能否保留？
6. Markdown 的 CommonMark、GitHub Flavored Markdown、数学公式和脚注扩展是否兼容？
7. 纯文本的段落边界如何定义？
8. 表格、图片、公式是否只保留“存在”，还是能够提取可检索语义？
9. 能否为每个文本块保留页码、坐标、字符偏移、标题路径和解析器版本？
10. 云端服务的模型版本、区域、限额和数据处理政策是否可接受？

## 3. 候选方案类别

### 3.1 独立解析库

| 方案 | 部署 | 适合格式 | 结构化能力 | 已知边界 |
|---|---|---|---|---|
| **PyMuPDF / MuPDF** | 本地 | PDF、图片 | 页面、块、行、span、字符、图片、坐标；可输出 text、blocks、words、DICT、RAWDICT | **F**：官方文档明确指出默认文本顺序可能不是自然阅读顺序，需要 `sort=True`；本身不是完整 OCR/语义理解方案 |
| **pdfplumber / pdfminer.six** | 本地 | 主要是文本型 PDF | 字符、线、矩形、图片位置、页码、表格、裁剪区域、搜索坐标 | **F**：README 明确称其更适合机器生成 PDF，不适合扫描 PDF；不提供 OCR，也不擅长 OCR 后表格 |
| **python-docx / OOXML** | 本地 | DOCX | 段落、段落样式、run、表格、图片、页眉页脚 | **F**：不支持旧 `.doc`；不能可靠计算最终视觉分页，脚注等内容支持不完整 |
| **CommonMark/GFM 解析器** | 本地 | Markdown | 标题、段落、列表、代码块、引用、链接等 AST | **F**：Markdown 方言差异明显；表格、脚注、数学公式通常是扩展，不应假设所有解析器一致 |

### 3.2 通用文档解析框架

| 方案 | 部署 | 适合格式 | 结构化能力 | 已知边界 |
|---|---|---|---|---|
| **Apache Tika** | 本地 Java 服务/库 | PDF、DOC/DOCX、HTML、TXT、Office 等 | 文件类型识别、文本和元数据统一接口 | **I**：官方定位偏“格式和内容抽取”；高级布局、复杂表格、公式和引用坐标需要单独验证 |
| **Docling** | 本地，可 CPU/GPU | PDF、DOCX、Markdown、TXT 等 | 统一 `DoclingDocument`；布局、阅读顺序、表格、代码、公式、图片、OCR；可导出 Markdown/HTML/JSON | **R**：依赖模型和额外资源；高级结构能力来自模型，中文、复杂双栏、公式仍需样本验证 |
| **Unstructured OSS** | 本地，也有 API/托管形态 | PDF、DOC/DOCX、Markdown、TXT、图片等 | `Title`、`NarrativeText`、`Table`、`Header`、`Footer` 等元素；可选页分隔、OCR、表格结构 | **F**：官方文档明确说明 `hi_res` 对多栏文档存在排序困难；`.doc` 需 LibreOffice 转换；DOCX 页码依赖页面渲染器插入分页 |

| 方案 | 部署 | 官方能力 | 限制和风险 |
|---|---|---|---|

## 5. 方案比较和技术边界

### 5.1 正文、页码、层级和段落

- **PDF 正文完整性**  
  **F**：PDF 文本通常是定位字符流，不一定包含语义段落。PyMuPDF 可以提供 block/line/span/char，但官方明确提醒默认顺序可能不自然。  
  **I**：单栏、规则排版通常风险较低；双栏、浮动文本框、边注会把“字符存在”与“自然阅读顺序”分离。  
  **C**：不能只用“抽取字符数”证明解析正确，必须加入阅读顺序和段落边界指标。

- **页码**  
  **F**：PDF 解析库可保留物理页面序号和坐标。  
  **R**：物理第 5 页不一定等于文档打印页码“3”；PDF 页码标签、封面和罗马数字需要单独测试。  
  **F**：Unstructured 的 DOCX 页码依赖显式分页和渲染器；python-docx 不能可靠获得最终页面布局。  
  **C**：PDF 可把 `physical_page` 和 `printed_page_label` 分开保存；DOCX 一期更适合用段落/标题路径和字符偏移引用，而不是承诺稳定页码。

- **标题和目录层级**  
  **F**：Markdown 标题层级是语法的一部分；DOCX 标题通常来自 Heading 样式；PDF 书签/目录可能缺失或只是普通文本。  
  **F**：Docling 文档说明支持从书签、编号和字体样式恢复标题级别，但该能力是可选恢复策略。  
  **R**：PDF 的字体大小并不等于标题语义，自动推断需在样本上验证。

- **段落边界**  
  **F**：Markdown 有明确 block 规则；TXT 只有换行和空行，通常没有语义段落。  
  **I**：PDF 段落是布局推断结果，页眉、页脚、脚注和文本框会造成误切分或粘连。  
  **C**：解析中间格式必须保留原始换行、块 ID 和坐标，不能只保存一份扁平纯文本。

### 5.2 特殊版式风险

| 场景 | 主要风险 | 一期处理建议 |
|---|---|---|
| 双栏 | 左右栏交错、跨栏标题、脚注顺序错误 | 作为强制实验样本；不通过时降级为页面级文本或人工确认 |
| 页眉页脚 | 每页重复内容污染检索，正文与页脚混合 | 保留 `Header/Footer` 类型，不直接删除原文 |
| 脚注 | 脚注可能插入正文、丢失引用关系 | 保存独立元素及其页码/坐标，暂不承诺语义合并 |
| 表格 | 无边框表格、合并单元格、跨页表格、OCR 表格错位 | 同时评价文本召回和单元格结构；跨页表格单独标记 |
| 图片 | 图片存在但没有语义；图片内文字可能漏掉 | 至少保留图片 bbox、页码和图注；图像理解作为增强能力 |
| 公式 | 字体编码、上下标、符号顺序和 OCR 误识别 | 保留公式区域截图或原始对象；不要把公式 OCR 结果当作精确文本 |
| 中文 | 无空格分词、字体映射、全角标点、竖排、OCR 字符混淆 | 采用字符级召回/CER，并测试中英文混排和标点 |
| 英文 | 连字符断词、ligature、大小写和行末换行 | 测试去连字符是否误合并词；保留原始文本和规范化文本两份 |

### 5.3 对后续检索、问答和引用的支持

建议所有候选工具统一转换到类似下面的内部记录：

```text
doc_id
source_hash
source_format
parser_name / parser_version / config
element_id
element_type
text
physical_page
printed_page_label
bbox
char_start / char_end
heading_path
parent_element_id
confidence
asset_ref
```

**C**：能够输出纯文本，不等于能够支持可靠引用。最低要求应是：

- 文本块可回溯到原始文档；
- PDF 块可定位到页码和 bbox；
- 标题路径与块关联；
- OCR 低置信度可被识别；
- 解析器版本和配置可复现；
- 表格、图片、公式不被静默丢弃。

## 6. 3-6 份授权样本的最小实验设计

建议使用 6 份小样本，每份 2-10 页即可：

1. **S1 文本型单栏 PDF**：中英文混排、标题、目录、页眉页脚、脚注、简单公式。
2. **S2 文本型双栏 PDF**：学术论文或技术报告，包含双栏、跨栏标题、表格、图片和参考文献。
3. **S3 扫描型中文 PDF**：中文正文、英文缩写、倾斜、低清晰度、印章或背景噪声。
4. **S4 DOCX**：Heading 1/2/3、自动目录、页眉页脚、分页符、表格、图片、脚注和中英文混排。
5. **S5 Markdown**：CommonMark/GFM 标题、嵌套列表、表格、代码块、链接、脚注、数学公式和图片链接。
6. **S6 纯文本 TXT**：UTF-8 与 GB18030 各一份，CRLF/LF、长行、空行、中文英文混排和特殊符号。

### 6.0 与现有基线衔接

实验开始前先复验 `experiments/minimal-chain-java` 的 `TECH-ARCH-001-R01`，记录其输入哈希、block 数量、标题路径、行号、检索命中和引用校验结果。该复验只作为 Markdown/TXT 基线，不与 PDF、OCR 或 DOCX 的解析结论合并。

解析器实验建议使用独立编号，并保留每次运行的原始输出、固定配置和失败日志：

| 实验编号 | 样本/目标 | 首轮目的 |
|---|---|---|
| `TECH-DOC-001-R01` | 文本型单栏 PDF | 正文、页码、阅读顺序和段落边界 |
| `TECH-DOC-002-R01` | 双栏 PDF | 栏顺序、跨栏标题、脚注和参考文献 |
| `TECH-DOC-003-R01` | 扫描型中文 PDF | OCR、中文/英文混排、低置信度标记 |
| `TECH-DOC-004-R01` | DOCX | 标题样式、表格、页眉页脚、脚注和分页边界 |
| `TECH-DOC-005-R01` | Markdown/TXT 扩展 | 方言、编码、换行和结构归一化 |
| `TECH-DOC-006-R01` | 表格/图片/公式样本 | 资产保留、结构恢复和降级展示 |

首轮不引入新的生产依赖，不改变现有 `MinimalChain` 的检索、模型或引用逻辑；先比较原始解析结果和统一 IR 映射，再决定是否需要扩展 `CanonicalDocument`/`DocumentBlock`。

### 6.2 实验步骤

1. 对每份样本建立人工参考标注：正文、标题级别、段落、页码、页眉页脚、脚注、表格、图片、公式。
2. 固定工具版本、模型版本、配置和运行环境。
3. 输出原始结果，不只保存 Markdown；同时保留 JSON、坐标、页码、日志和失败信息。
4. 对每个工具进行文本、结构、布局和引用定位对照。
5. 记录失败样例的截图、原始页、输出片段和错误类别。
6. 只对授权样本进行云端测试，并记录上传区域、模型版本、处理时间和费用。

## 7. 需要记录的指标

### 7.1 内容和结构

- 正文字符召回率；
- OCR 字符错误率 CER、英文词错误率 WER；
- 阅读顺序正确率；
- 段落边界 Precision/Recall/F1；
- 标题识别 Precision/Recall/F1；
- 标题层级准确率；
- 页码映射准确率；
- 页眉页脚误归入正文比例；
- 脚注保留率；
- 表格单元格文本准确率；
- 表格结构准确率：行、列、合并单元格；
- 图片/公式检测召回率；
- 中英文混排和特殊符号错误率。

### 7.2 工程和服务

- 单页和整文档处理延迟，p50/p95；
- CPU、内存、GPU 使用量；
- 失败率、超时率、异常类型；
- 批量处理吞吐；
- 输出大小；
- 版本升级前后结果差异；
- 云服务费用、限额、区域和数据留存政策。

### 7.3 下游可用性

- 给定查询命中正确页码的比例；
- 引用 bbox 是否覆盖答案证据；
- 标题路径是否随检索块保留；
- OCR 低置信度内容是否可被标记；
- 表格/公式是否被错误地当作普通段落。

## 8. 失败场景和降级方案

| 失败场景 | 降级方案 |
|---|---|
| 文本型 PDF 阅读顺序错误 | 保留页面级文本；按列裁剪后分别提取；必要时显示“布局不保证” |
| 扫描 PDF OCR 置信度低 | 降级为 OCR 文本 + 原页截图；标记低置信度；允许用户查看原页 |
| 中文混排字符错误 | 保存原图、OCR 文本和字符置信度；不对低置信度内容做强断言 |
| 表格结构无法恢复 | 保留表格截图和线性化文本；不承诺单元格级问答 |
| 公式无法识别 | 保留公式图片/bbox；不把错误 OCR 结果当作公式文本 |
| 页眉页脚污染正文 | 保留元素类型；检索时默认降权而不是删除 |
| DOCX 无稳定页码 | 使用章节路径、段落索引和字符偏移作为引用 |
| `.doc` 转换失败 | 一期仅支持 `.docx`，`.doc` 进入转换或人工处理队列 |
| 云服务超限、不可用或费用不可控 | 本地基础解析作为兜底；限制文件大小和页数；异步处理 |
| 云模型升级导致结果漂移 | 固定模型版本；保存原始 JSON；升级前重跑回归样本 |

## 9. 对一期范围和待决策事项的影响

以下是**候选范围边界，不是最终选型**：

- Markdown 和纯文本的结构化风险最低，适合作为基线格式。
- DOCX 的正文、标题样式和表格通常可提取，但最终分页和脚注需要谨慎承诺。
- 文本型单栏 PDF 可作为基础支持候选。
- 双栏、扫描 PDF、复杂表格和公式应作为“实验通过后支持”的条件格式。
- 扫描 PDF 若纳入一期，应明确是“本地 OCR/云 OCR 的最佳努力结果”，而不是等同于文本型 PDF。
- PDF 引用定位可优先承诺“物理页码 + bbox”；DOCX、Markdown、TXT 需要采用段落/行号/字符偏移等替代定位。
- 如果一期必须支持复杂表格、公式或高质量中文 OCR，托管服务可能降低开发工作量，但会引入隐私、费用、区域和版本依赖。
- 如果一期要求完全本地部署，则应接受更窄的格式范围或更明确的降级体验。

- `TECH-DOC-006`：扫描 PDF 中文 OCR、英文 OCR 和中英文混排 CER/WER。
- `TECH-DOC-007`：表格文本准确率、单元格结构和跨页表格处理。
- `TECH-DOC-008`：图片、图注、公式区域检测与降级展示。
- `TECH-DOC-009`：DOCX 标题样式、表格、页眉页脚、脚注和分页稳定性。

本文件没有给出最终解析器选型，也没有把任何厂商宣传直接转化为项目验收结论。所有准确率、布局稳定性、中文 OCR 质量和下游引用效果，都必须通过授权样本和固定版本的最小实验验证。
