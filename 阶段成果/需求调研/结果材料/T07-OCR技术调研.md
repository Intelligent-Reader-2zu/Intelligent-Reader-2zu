# T07 OCR 技术环节调研与最小实验设计

> 项目：智能笔记助手——内置 AI 助手的智能阅读器  
> 范围：扫描型 PDF、图片文档、低质量扫描件的 OCR、版面分析与下游证据链  
> 文档性质：候选方案与验证设计，不是最终技术选型或产品能力承诺  
> 调研日期：2026-09-28

## 0. 先读现有证据：本工作区已经知道什么

本项目没有现成的 OCR 产品链路。已有材料证明的是“候选可以被安装和调用”，不是“扫描文档已经可靠支持”。相关证据如下：

| 证据 | 已观察事实 | 不能推出的结论 |
|---|---|---|
| `experiments/parser-benchmark/samples/self-authored/pdf/SELF-004-scanned.pdf` | 2 页、图像型、中文/英文缩写、轻微倾斜和噪声；项目组自制，默认禁止云端上传 | 不代表真实扫描件分布，也没有逐字金标准 |
| `results/candidate-pdf/SELF-004.docling.json` | Docling 2.130.0 对当前 `SELF-004`（SHA-256 `ab008...`）重跑返回 2 页、16 个文本元素、0 个表格，约 26.1 秒；输出含 `page_no` 和 bbox | 不能据此计算 CER/WER、表格准确率或生产时延；自制样本仍不能代表真实扫描件 |
| `results/candidate-pdf/unstructured-ocr_only-summary.json` | Unstructured 0.27.8 + Tesseract `chi_sim/eng` 对当前哈希在 Windows hOCR 路径仍以 `XMLSyntaxError` 失败 | 不能说 Unstructured 在所有环境失败；只能记录当前组合、当前环境和当前样本失败 |
| `results/ocr-baseline/summary.json` | Tesseract 5.5.3 对当前 `SELF-004`（SHA-256 `ab008...`）以 144 DPI、PSM 3 运行，2 页均返回；页耗时约 2355/2466 ms，词级平均置信度约 91.34/91.55 | 置信度不是准确率；尚无逐字参考答案，不能宣布 OCR 质量达标；样本哈希不同，不能和旧 Docling 结果做质量/时延排名 |
| 现有 `T07-文档解析技术调研.md` | 已定义 `TECH-DOC-006` OCR、`TECH-DOC-007` 表格、`TECH-DOC-008` 公式等验证项 | 这些是待验证事项，不是完成状态 |

实验环境还记录了 Tesseract 5.5.3.20260724、语言包 `eng`/`chi_sim`、Python 3.13.2。Docling 在 Windows 中文路径曾要求 ASCII 临时目录和缓存目录；该现象应作为复现风险登记，而不是泛化为产品限制。

**样本版本约束**：2026-09-24 的 Docling/Unstructured 结果引用 `SELF-004` 哈希 `643a...`，当前文件和本次 Tesseract 基线为 `ab008...`。后续正式对比必须让所有候选重跑同一哈希；本文件只把旧结果作为历史可运行性/失败证据。

### 0.1 当前新增的独立实验结果

已在当前 `SELF-004` 上完成两个 Tesseract 实验：

- `TECH-OCR-001-R01`：6 组 DPI/PSM/二值化配置。原图、144 DPI、PSM 3 的全字符 CER 为约 **2.11%**，平均端到端页时延约 **2442 ms**；300 DPI 并未在这个样本上带来更低 CER，且平均耗时更高。结果和每页 JSON 在 `experiments/parser-benchmark/results/ocr-tesseract-matrix/`，脚本为 `run_ocr_tesseract_matrix.py`。
- `TECH-OCR-002-R01`：原图、模拟降采样、模糊、低对比度+噪声、额外旋转 3° 五种变体。全字符 CER 分别约为 **6.33%、10.24%、11.14%、6.93%、4.22%**。平均置信度仍约 88～90，不能把置信度当作准确率。结果在 `experiments/parser-benchmark/results/ocr-degradation-matrix/`，脚本为 `run_ocr_degradation_matrix.py`。
- `TECH-OCR-009-R01`：用 9 个固定关键字符串做页面级关键词召回，降采样变体召回为 0.667，其余当前变体为 1.0；它不是语义检索、证据片段召回或引用 bbox 覆盖率实验。详见 `experiments/parser-benchmark/results/ocr-downstream/`。
- `TECH-OCR-015-R01`：RapidOCR 3.9.2 + ONNX Runtime（隔离环境已有 PP-OCRv6 small 模型）在同一 `SELF-004` 上两页均成功，返回行文本、四点 polygon bbox 和置信度；本次运行 144 DPI 平均 CER 约 **4.22%**、中文 CER **0**、英文/数字 WER 约 **8.33%**、关键字符串页面召回 **1.0**，OCR 页耗时约 **2508 ms**。300 DPI 平均 CER 约 **4.52%**、中文 CER **0**、英文/数字 WER 约 **16.67%**、页耗时约 **2093 ms**。全字符误差主要来自行/区域顺序和英文数字分组，而非本样本的中文字符替换；这不等于复杂版面已解决，时延需用 p50/p95 重复测量。原始 JSON 和报告在 `experiments/parser-benchmark/results/ocr-rapidocr/`，脚本为 `run_ocr_rapidocr.py`。
- `TECH-OCR-016-R01`：PaddleOCR `2.10.0` 与 PaddlePaddle `3.3.1` 安装、模型下载和初始化成功，但两页均在 OneDNN `fused_conv2d` 推理阶段失败；这是 Python 3.13/Windows 当前版本组合的环境阻塞，不是识别质量结论。
- `TECH-OCR-016-R02`：在项目内独立 Python `3.11.16` 环境改用 PaddlePaddle `2.6.2` 后，两页、144/300 DPI 均成功；144 DPI 全字符 CER 约 **8.43%**、中文 CER **0**、英文/数字 WER 约 **41.67%**，热运行 p50/p95 约 **677/1278 ms/页**。高置信度下仍有英文/数字粘连和行顺序错误。
- `TECH-OCR-017-R01`：OCRmyPDF `17.12.1` 的 `sandwich` 路径成功生成两页可搜索 PDF，页数、页面尺寸和可视原图保留；英文/数字查询可命中，但中文文本层经 `pypdf` 提取为乱码，当前不能进入中文检索或引用主路径。
- `TECH-OCR-018-R01`：PP-StructureV2 的布局-only 路径处理 4 页成功；双栏样本检测到标题、正文、参考文献、页脚和表格区域，但扫描页被整页误分为 `figure`。完整表格模型与 PaddlePaddle 2.6.2 初始化不兼容，未产生单元格/HTML 质量结果。
- `TECH-OCR-019-R01`：EasyOCR `1.7.2` 与 PyTorch `2.14.0+cpu` 在独立 Python 3.11 环境可导入和执行张量运算，但模型下载端点的证书链被默认 CA 和 Windows 系统证书同时拒绝；未进入推理，不能形成质量结论。
- `TECH-OCR-020-R01/R02/R03`：PP-StructureV3 `3.7.0` 已在独立 Python 3.11/PaddlePaddle 3.3.1 环境运行。默认 OneDNN 路径失败；关闭 MKL-DNN 后，双栏表格页成功并恢复 3x3 网格和 9 个单元格框，但 HTML 只有 5/9 个单元格内容位于正确位置，页面耗时约 **823.1 s**。原尺寸扫描页在独立进程中仍原生退出；缩小到 1000x1414 后成功，全字符 CER 约 **0.60%**、中文 CER **0**、英文/数字 WER **33.33%**，页面耗时约 **118.6 s**。模型缓存约 **901 MiB**。这是结构/运行时风险证据，不支持进入一期同步主链路。
- `TECH-OCR-021-R01`：RapidOCR 在与 Tesseract 相同的五组退化图上全部成功并返回 bbox；全字符 CER 为 **4.22%-8.73%**，中文 CER 为 **0**，英文/数字 WER 为 **0%-16.67%**，关键字符串页面平均召回均为 **1.0**。高置信度和关键词命中仍可能与较高 CER/WER 同时出现，不能作为自动放行依据。
- `TECH-OCR-022-R01`：按暂定一期门槛统一检查 6 个清晰页配置，只有 **RapidOCR 144 DPI** 同时通过字符、英文数字、11 个查询预期页召回和行 bbox 定位。Tesseract 300 DPI 字符指标通过，但 `A-01 0.95` 在第一页未被精确定位；PaddleOCR 2.10 的英文/数字 WER 未通过。两种引擎在五组退化页上均没有一个满足全部暂定门槛。
- `TECH-OCR-023-R01`：从 PaddleOCR 官方仓库固定提交 `dab3fe3...` 按 Git blob SHA 获取公开图片和文本层 PDF 负控，记录仓库路径、SHA-256、Apache-2.0 许可证文件、上游图片权利边界、排除样本和 `cloud_upload_allowed=no`。浏览器访问受网络阻断后改用证书校验成功的 GitHub REST API，没有关闭 TLS 校验。
- `TECH-OCR-024-R01`：RapidOCR/Tesseract 在 8 张公开图上运行成功率均为 8/8，但固定问题仅通过 **4/11** 和 **3/11**。两者均未恢复 180 度页面；RapidOCR 在中文奖牌表/小表格的平均置信度达 **98.92/99.91**，但仍未保持同一行关系。4 页文本层 PDF 负控被正确判为 `skip_ocr`。
- `TECH-DOC-candidate-docling-default`：使用当前哈希、ASCII 临时目录重跑 Docling 2.130.0，2 页成功、16 个文本元素、0 个表格，约 **26.1 s**；仍未做 CER/WER、表格结构或引用 bbox 覆盖率。

这些结果只支持五个局部判断：预处理不是必然增益；低清/模糊会显著增加字符和英文数字错误；RapidOCR 的 polygon 定位接口可用，但倾斜页的区域/行顺序仍需单独评分；置信度需要用金标准校准；公开复杂样本中的 token 命中不能替代表格、公式或印章结构。逐字金标准仍只有两页自制样本，公开集也没有完整人工转写，并且手写仍未实测，不能据此完成最终选型或承诺一期质量。额外 3° 旋转在合成样本上得到较低 CER，可能受旋转方向和图像重采样影响；真实 180 度页面两引擎均未通过，更不能外推为“旋转越大越好”。

## 1. 调研目标和结论口径

需要回答的是：在中文、英文、中英文混排、低清晰度、倾斜、印章/手写标记、多栏、表格、公式和特殊符号场景下，哪类方案值得进入独立最小实验；OCR 结果能否保留页码、bbox、版面和置信度；错误会怎样影响检索、问答和引用；一期应承诺到什么程度。

每条结果使用以下口径：

- **F（事实）**：来自固定版本运行结果、官方 API/限制或可复核原始文件。
- **I（解释）**：对事实的工程含义，不等同于能力承诺。
- **C（建议）**：用于范围、指标或降级的建议。
- **R（待验证）**：必须用项目样本和固定配置实测。

公开文档中的“支持某格式/布局”只能登记为 F（厂商声明），不能改写成项目 C。项目结论必须来自相同样本、相同问题集和保留原始响应的对照实验。

## 3. 候选方案类别与对比

### 3.1 方案类别

| 类别 | 代表候选（待实测） | 能解决的问题 | 主要边界 |
|---|---|---|---|
| 本地 OCR 引擎 | Tesseract；PaddleOCR；RapidOCR/ONNX 组合 | 图像转文字、语言包、词/行 bbox；离线和隐私可控 | 版面、表格、公式常需另加模块；模型和预处理影响很大 |
| 本地版面分析 OCR | Docling；PaddleOCR PP-Structure/相关布局模型；Unstructured `hi_res`/`ocr_only` | 页面区域、阅读顺序、标题、表格、图片和 OCR 的组合 | 模型资源、CPU/GPU、中文多栏和复杂表格需要样本验证 |
| 低层 PDF + OCR 组合 | PyMuPDF/pdfplumber + 独立 OCR | 保留物理页、原图、bbox，便于可解释兜底 | 需要自己做版面排序、去重和统一 IR；不是“一键布局理解” |
| 云端 OCR/文档分析 | Azure Document Intelligence Layout；Google Document AI Layout Parser；AWS Textract；Unstructured API | 托管模型、扩展能力、表格/页面/置信度接口和较少本地运维 | 上传、费用、区域、配额、版本漂移、网络失败和数据合规；项目准确率未测 |

### 3.3 尚未测的本地候选与投入顺序

| 候选 | 当前状态 | 值得验证的独立问题 | 优先级与阻塞 |
|---|---|---|---|
| PaddleOCR 3.x / PP-OCR 系列 | 3.7.0 已在隔离环境随 PP-StructureV3 运行 PP-OCRv5 server 检测/识别；需先导入 PyTorch并固定 ASCII 缓存目录 | 若继续，应只补轻量模型与已有 RapidOCR/PaddleOCR 2.x 的同页质量/资源差异 | **中低**；server 模型已显示高 CPU 成本，同一模型家族不再优先扩张 |
| PP-StructureV3 | 已完成 R01-R03；V2 表格初始化阻塞已绕过，V3 能返回表格结构 | 仍需真实表格、合并单元格、GPU、页级隔离和资源门控 | **已验证、受限**；CPU 同步主链路不合适，表格只作 `table_uncertain` 异步增强；见 `TECH-OCR-020` |
| OCRmyPDF 17.12.1 + Tesseract | **已运行**：`sandwich` 成功生成两页可搜索 PDF，页数/尺寸和视觉保留；中文文本层经 `pypdf` 提取为乱码 | 生成可搜索 PDF 时是否保留页数、旋转、文本层、原图和可复核坐标 | **受限**；可做原页封装实验，但当前中文文本层不可进入检索；见 `TECH-OCR-017-R01` |
| EasyOCR 1.7.2 | 独立 Python 3.11/PyTorch CPU 环境可运行；模型下载受不受信任证书链阻塞，未推理 | 作为另一条中英 OCR 对照，关注安装体积、CPU 时延和低清差异 | **环境阻塞**；应由受信任制品库离线提供经哈希校验模型，不关闭 TLS 校验；见 `TECH-OCR-019-R01` |
| Surya OCR/布局/表格 | 未安装，模型和运行资源较大 | 英文/多语言版面、阅读顺序和表格区域 | **中低**；中文和 Windows/CPU 可用性先做 smoke test，再决定是否纳入主矩阵 |
| docTR / MMOCR | 未安装，分别偏通用深度学习 OCR 与研究框架 | 作为模型/检测器替换对照，验证可训练性和 bbox 输出 | **低**；依赖和模型组合复杂，不适合作为一期默认链路 |
| Windows.Media.Ocr | 未接入，Windows 系统 API 候选 | 零额外模型安装的本地快速兜底；语言包、坐标和页级接口 | **低**；跨版本、语言包和质量需单独验证，不能替代主引擎 |
| ABBYY FineReader Engine（商业本地 SDK） | 未采购/未测 | 商业 OCR、表格和版面能力的本地部署对照 | **条件性**；需确认授权、价格、离线部署和数据驻留，不能与开源免费成本直接比较 |
| Kraken / Calamari | 未安装，偏历史文献/可训练模型 | 老字体、历史扫描和可训练识别器的适配性 | **低**；除非一期明确面对历史档案或需要自定义训练 |
| 公式专用识别器（pix2tex、Nougat/Math OCR 类） | 未测 | 公式区域检测、LaTeX/MathML、上下标和特殊符号 | **专项**；不能把普通 OCR 输出当公式结果，优先以区域截图降级 |

当前高优先级本地家族已经覆盖 Tesseract、RapidOCR、PaddleOCR、PP-Structure、Docling、Unstructured 和 OCRmyPDF。下一步优先级应从“继续增加同类引擎”转为**补齐印章/手写/公式/真实低质扫描样本与统一下游问题集**。EasyOCR 仅在取得受信任离线模型后复测；Surya/docTR/MMOCR 保留为中低优先级替代，不在一期证据不足时继续扩大依赖面。

### 3.4 推荐的比较原则

- 首轮只比较“同一页图、同一 DPI、同一语言设置、同一问题集”；不要把一个方案的最佳配置和另一个方案的默认配置直接比较。
- 记录完整原始 JSON/TSV、模型/语言包、预处理、硬件和版本；同时保存原页图和源哈希。
- 云端只使用 `cloud_upload_allowed=yes` 的公开或明确授权样本，先设置预算与页数上限；普通样本也不能默认允许外传。
- 质量、结构保留和工程成本分开评分；一个高 CER 但能定位 bbox 的结果与一个文本较顺但无证据坐标的结果，不能只用“文本好坏”排序。

问题必须同时测试 OCR、布局、检索和引用，不只看 OCR 文本预览：

| 编号 | 问题 | 通过所需证据 | 主要失败归因 |
|---|---|---|---|
| Q-OCR-001 | 页面上“低清”一词出现在哪一页？ | 正确 `physical_page` + bbox | 字符错误、页码映射 |
| Q-OCR-002 | 原文中的英文缩写和数字 `12345` 是什么？ | 中英文及数字精确匹配 | 混排、大小写、数字误识别 |
| Q-OCR-003 | 表格区域中 `A-01` 对应的数值和说明是什么？ | 单元格/区域 bbox；若结构失败则原图证据 | 表格线性化、列错位 |
| Q-OCR-004 | 两栏页面中左栏第一段和右栏第一段的先后关系是什么？ | 阅读顺序和两段 bbox | 栏交错、跨栏标题 |
| Q-OCR-005 | 印章/手写内容是否属于正文？ | 标记区域类型和原图回看 | 章印污染、手写误读 |
| Q-OCR-006 | 公式中的上下标、运算符和特殊符号能否逐项复述？ | 公式区域截图 + 结构化公式（若有） | 普通 OCR 误读公式 |
| Q-OCR-007 | “第 3 页”是物理页号还是打印页码？ | 两个字段分别返回 | 页脚误识别、页码标签丢失 |
| Q-OCR-008 | 查询一个只存在于低置信度区域的词 | 命中但显式低置信度，或拒绝强断言 | 检索放大 OCR 错误 |
| Q-OCR-009 | 查询原文不存在的词 | 无证据时拒答，不生成猜测 | OCR 噪声导致幻觉 |
| Q-OCR-010 | 同一词跨页/跨栏出现时引用哪个位置？ | 引用覆盖实际证据字符和 bbox | 分块、去重、阅读顺序 |

`SELF-004` 已有固定查询“`OCR TEST`”“物理页码”“低清”和预期证据片段；本轮应扩展为逐字标注，而不是修改原文件或把输出反写成真值。

### 4.3 独立运行矩阵

1. **基线**：Tesseract `chi_sim+eng`，PSM 3，144/300 DPI，两种预处理（原图、去噪/倾斜校正）。
2. **引擎对照**：固定 PaddleOCR/PP-Structure 或 RapidOCR 版本；同页图和同一语言配置。
3. **版面对照**：Docling、PP-Structure、Unstructured（修复后）分别输出元素、区域和表格结构。
4. **下游对照**：相同分块和检索参数，把 OCR 输出送入关键词检索；只替换 OCR/布局模块。
5. **云端对照**：授权条件满足后，逐服务单独运行；保存请求 ID、区域、模型版本、费用和原始响应。云端失败不得用本地结果替代记录。

## 5. 指标：识别质量、结构保留、下游和时延

### 5.1 识别质量

- 中文 CER：按字符编辑距离计算，分别报告正文、表格、页脚、印章/手写区域；不要把空白和标点规则混在一个分数中。
- 英文 WER、大小写/连字符错误率；中英混排再报告混排 token/字符错误。
- 数字、单位、日期、版本号和特殊符号精确率；这些错误对检索和问答常比普通字错更严重。
- 区域检测 Precision/Recall：正文、页眉、页脚、表格、图片、公式、章印、手写。
- 置信度校准：低/中/高置信度桶的实际 CER；不能只报告平均 confidence。

建议验收阈值先写成“待基线后确定”，不预先假设厂商目标。若必须做一期门槛，应按场景设最低值，例如：正文 OCR、数字/关键词、引用定位分别设门槛；公式和手写不得用正文 CER 代替。

### 5.2 结构保留

- 阅读顺序准确率：参考顺序中的相邻块或 token 保持比例；双栏单独报告。
- 段落边界 Precision/Recall/F1；标题和层级 F1。
- 表格：单元格文本准确率、行/列识别、合并单元格、跨页连接；表格截图/原图保留率。
- 公式：公式区域召回、符号/上下标准确率；没有可靠结构时以“区域检测 + 原图可回看”计分，不把普通 OCR 当公式真值。
- 页码：`physical_page` 正确率、`printed_page_label` 正确率、bbox 覆盖率。
- 证据链完整率：每个检索块/回答引用能否回到 `source_hash + page + bbox + 原图裁剪`。

### 5.3 下游影响

- 查询召回@k、正确页命中率、证据片段召回率；分别在原文查询、OCR 错写查询和数字/公式查询上测。
- 引用支持率：回答中的关键断言是否被引用 bbox 覆盖；引用页码错误单独计为严重错误。
- 无依据拒答率：只在低置信度 OCR 噪声中出现的词，不应诱导模型编造。
- 检索污染率：页眉/页脚/章印/手写被当作正文并进入 top-k 的比例。
- 低置信度可见率：低置信度字符是否在检索、问答和界面层保持警告。

### 5.4 工程指标

- 单页/整文档处理时间 p50/p95，冷启动与热启动分开；首次模型下载单独记录。
- CPU、内存、GPU、模型缓存大小、批处理吞吐、失败/超时率。
- 云端：按页或请求的实际费用、API 配额、重试次数、区域、数据驻留和版本漂移。
- 可复现性：源文件哈希、渲染 DPI、预处理参数、语言包/模型哈希、解析器版本和配置哈希齐全。

## 6. 常见失败场景及对检索、问答、引用的影响

| 失败场景 | 直接表现 | 下游风险 | 必须保留的证据 |
|---|---|---|---|
| 中文形近字/标点错误 | 查询词未命中或命中错词 | 召回下降、问答遗漏 | 原图、原 OCR、字符/词置信度 |
| 英文连字符、大小写、数字误识别 | `A-01`、版本号、单位改变 | 精确检索和引用断裂 | 原始 token、规范化副本、bbox |
| 中英混排切分异常 | 英文被粘到中文或反之 | 分词、实体和引用范围错 | 词/字符跨度与语言配置 |
| 倾斜/低清/折痕 | 漏行、重复行、低置信度 | 关键段落不可检索 | 页图、预处理前后图、失败原因 |
| 印章或手写被当作正文 | 章印/批注混入文本 | 问答把批注当事实 | 区域类型、原图裁剪、人工标记 |
| 双栏交错 | 左右栏顺序反转 | 跨段推理错误，引用指向错误栏 | 区域 bbox、栏 ID、页级文本 |
| 表格扁平化/列错位 | 行列关系丢失 | “A 列数值”回答错误 | 原图、表格网格、线性化文本双存 |
| 公式/特殊符号误读 | `−`、`≤`、上下标改变 | 结论、条件和计算错误 | 公式截图/bbox；无法结构化时禁止强断言 |
| 页眉页脚混入 | 重复词进入正文索引 | top-k 被页脚污染 | `Header/Footer` 类型和检索降权标记 |
| 物理页与打印页混淆 | 引用显示错页 | 用户无法复核，信任下降 | `physical_page` 与 `printed_page_label` 分开 |
| OCR 输出无 bbox/页码 | 只有扁平文本 | 无法可靠引用 | 原页截图和“定位不可用”状态 |
| OCR 引擎/服务不可用 | 空结果、超时、服务错误 | 上传失败或链路阻塞 | 异常、版本、重试和输入哈希 |

## 7. OCR 失败时的降级策略

按“证据不丢失、错误不静默”的原则实现：

1. **先判定输入**：存在文本层时优先保留原文本层；无文本层才进入 OCR。两条结果都保存，不覆盖原文件。
2. **质量门控**：按页面和区域计算置信度/异常率；低于阈值的区域标为 `low_confidence`，不作为无条件问答证据。
3. **原页可回看**：始终保留页图、原始 OCR、词/行 bbox 和可点击裁剪；用户可以核对原文。
4. **检索降级**：OCR 质量不足时允许页面级全文搜索、模糊匹配或人工输入校正；禁止把低质量结果当作精确全文。
5. **问答降级**：证据低置信度、公式/表格结构失败或引用 bbox 缺失时，回答应说明不确定性，必要时拒答并给出原页位置。
6. **布局降级**：多栏顺序不确定时按栏/页面分开索引；表格结构失败时提供原图 + 线性化文本；不静默合并。
7. **引擎回退**：本地 OCR 失败可切换第二本地引擎；云端只在授权和网络策略允许时使用。云端失败不能自动把敏感文档外传。
8. **人工复核队列**：低置信度页、印章/手写、关键数字/公式进入人工校正；校正结果要保留操作者、时间和版本，不覆盖原始 OCR。
9. **完全失败**：保留原文件和错误状态，提供原页阅读；检索/问答显示“未建立可靠文本证据”，而不是返回空白或猜测。

建议内部状态至少区分：`text_layer`、`ocr_ok`、`ocr_low_confidence`、`layout_uncertain`、`table_uncertain`、`formula_image_only`、`ocr_failed`。

## 8. 本地 OCR、版面 OCR、云端 OCR 的取舍

| 维度 | 本地 OCR 引擎 | 本地版面分析 OCR | 云端 OCR/文档分析 |
|---|---|---|---|
| 质量 | 可通过预处理和模型替换调优；由本项目实测决定 | 更可能输出区域/结构，但复杂中文、表格和公式仍需实测 | 可能减少模型运维，但服务宣传不等于项目样本质量 |
| 成本 | 无按页费用；需承担 CPU/GPU、开发、模型和维护 | 模型缓存和推理资源较高，冷启动可能明显 | 通常按页/请求计费，重试、存储和最低消费要计入 |
| 隐私 | 原始文件不出本机，最容易满足敏感资料要求 | 同本地；需管理模型和日志 | 需确认区域、留存、训练使用、DPA、凭证和授权 |
| 部署 | 可离线；依赖安装和语言包管理 | 依赖更多，可能需要容器/GPU/ASCII 缓存路径 | 网络、账号、配额、限流和服务可用性是硬依赖 |
| 可复现 | 版本和模型固定后较好 | 模型/硬件差异需记录 | 模型升级和服务端变化可能导致漂移，必须保存请求元数据 |
| 适合一期 | 作为离线基线和兜底 | 仅在结构指标通过后承担主路径 | 仅限获授权普通资料的可选增强，不作为敏感文档隐式依赖 |

## 9. 对一期扫描 PDF 支持范围的建议

这是范围建议，不是最终选型：

- **建议承诺**：仅对清晰、近似正向、印刷体、单栏、中文/英文/混排扫描 PDF 提供“最佳努力 OCR”；保存物理页、原页图、文本块/词 bbox、置信度和处理状态，并经过页级质量门控。
- **实验性支持**：轻微倾斜、轻度噪声和低清页。当前 Tesseract/RapidOCR 在五组退化页上均未满足全部暂定门槛，因此一期不得承诺这些页面必然准确；应进入 `ocr_low_confidence`、第二引擎重试或人工复核。
- **受限支持**：双栏、无边框/合并/跨页表格、印章和手写标记、公式和特殊符号。默认展示原图和警告，不承诺结构化问答或精确公式。
- **暂不承诺**：严重模糊、遮挡、复杂手写、竖排/古籍字体、关键财务/法律数字的无人工复核识别。
- **一期架构建议**：先采用“文本层检测 -> 本地 OCR 基线 -> 版面/表格增强（实验通过后） -> 质量门控 -> 原页降级”的可替换适配器；云端作为明确授权且允许出域时的独立分支。
- **一期候选实现**：RapidOCR 144 DPI 作为清晰页主候选，Tesseract 300 DPI 仅作第二本地引擎重试。两者结果不得静默拼接；主引擎或重试任一不满足字符、精确编号、查询和定位门槛时，都降级到原页复核。
- **公开样本复测约束**：`TECH-OCR-024-R01` 中 RapidOCR/Tesseract 在 180 度实拍页均未通过；RapidOCR 在中文奖牌表和小表格上即使平均置信度达到 `98.92/99.91`，仍未保持同一行关系。因此一期不把自动纠正倒置页、表格 token 拼接或高置信度结构问答列为支持能力。
- **硬约束**：任何 `cloud_upload_allowed` 为 `no/unknown` 的文件不得自动发送云端；扫描 OCR 结果不得替代原始页作为唯一引用证据。

## 11. 当前结论与未决问题

当前证据支持“本地 OCR 和版面 OCR 可以进入独立验证”，不支持任何最终工具选型。Tesseract 是已可运行的本地基线；Docling 是值得继续测量结构和资源成本的本地组合；Unstructured 当前 Windows 中文 hOCR 组合应先修复或替换；云端服务因授权、费用和隐私前置条件尚未实验。

PaddleOCR 的 Python 3.13/PaddlePaddle 3.3.1 组合失败，但 Python 3.11/PaddlePaddle 2.6.2 组合已成功进入质量对照。它在当前小样本上中文字符正确、CPU 推理较快，但英文/数字分组和行顺序明显弱于字符级指标所显示的质量。PP-StructureV2 layout-only 可运行；PP-StructureV3 进一步跑通了表格结构链，但 CPU 时延、原尺寸进程退出、阅读顺序缺口和 5/9 单元格位置准确率使其目前只能作为离线增强实验，不能把公开结构能力描述当作项目结论。

OCRmyPDF `17.12.1` 已完成两页封装验证：`sandwich` 渲染器能保留页数、页面尺寸和可视原图，英文/数字固定查询可命中；默认 hOCR 路径仍受中文 XML 编码错误影响，而 `sandwich` 输出的中文文本层经 `pypdf` 提取为乱码。当前只能将其视为受限封装/降级候选，不能将该 PDF 文本层直接用于中文检索、问答或引用。

按 `TECH-OCR-022-R01` 的暂定门槛，RapidOCR 144 DPI 是当前唯一通过清晰页全部指标的本地主候选；Tesseract 300 DPI 只能作为第二引擎重试，PaddleOCR 2.10 不承担精确英文/数字主路径。退化矩阵没有任何引擎全项通过，因此一期扫描 PDF 范围必须保持“清晰单栏最佳努力 + 失败可见”，不能把轻度模糊、低清或倾斜写成稳定支持。

`TECH-OCR-023/024` 又补充了固定提交的公开图片证据：RapidOCR/Tesseract 图片运行成功率都是 8/8，但固定问题只通过 4/11 和 3/11；两者都没有恢复 180 度页面。双栏正文能命中少量关键字但存在阅读顺序/公式结构风险；表格和印章则出现“高置信字符存在、关系或区域类型仍失败”。这进一步证明 OCR 置信度和关键词召回不能单独作为检索、问答或引用放行条件。

仍需项目负责人确认：一期是否必须支持扫描 PDF；低置信度内容是提示、降权还是禁止回答；复杂表格/公式是否进入验收；允许哪些样本出域；目标硬件和 p95 时延；引用要求是页级还是 bbox 级。没有这些硬约束，不能把公开基准或厂商宣传转成一期承诺。
