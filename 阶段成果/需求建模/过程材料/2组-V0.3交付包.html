2.1 关系修订明细

R-01｜导入 → 处理并索引（extend 改为 include）

V0.2：  UC02 ..> UC01 : <<extend>>      （处理并索引 扩展 导入文档）
V0.3：  UC01 ..> UC02 : <<include>>     （导入文档 包含 处理并索引）

修订理由：

  1. UC02 的前置条件本身写的是"文档已登记"，说明处理总是在导入之后发生，是必经步骤而非可选扩展；
  2. 格式不支持、权限不足等失败分支仍由 UC02 的异常路径承载（ParseRun.status = failed），不影响 include 的成立；
  3. 原写法会让读者误解为"用户可以只导入不处理"，与 UC03"查看文档状态"依赖处理结果的设定冲突。

R-02｜核验引用的宿主用例（重新挂载 extend）

V0.2：  UC09 ..> UC08 : <<extend>>      （创建批注/笔记 扩展 核验回答引用）
V0.3：  UC08 ..> UC06 : <<extend>>      （核验回答引用 扩展 对文档/选中文本提问）
        UC08 ..> UC07 : <<extend>>      （核验回答引用 扩展 生成摘要/要点）
        移除 UC09 ..> UC08

修订理由：

  1. 核验引用是用户在看到一条带引用的回答之后才会做的可选动作，其宿主必然是被核验的两类回答用例 UC06 与 UC07；
  2. 创建批注/笔记与核验引用之间是数据关联（领域模型中 Note "0..*" --> "0..1" Answer、Citation、Evidence），V0.2 把它写成行为扩展属于关系类型误用；
  3. 该修订不影响 UC08 的参与者与主成功路径，仅修正其挂载位置。

说明：此条相对 2 组建模任务分工书 §4 中"修正两处关系方向"的表述略有扩展——UC09 与 UC08 之间不是方向问题而是关系类型问题，故按语义重挂而非简单反向。如组内评审认为应保守处理（仅反向为 UC08 ..> UC09 : <<extend>>），可在评审会上提出由组长裁决。

2.2 易混术语辨析（必须区分）

易混对 区别
Evidence 证据 vs Citation 引用 证据是原文片段本身；引用是回答里指向某条证据的落点（含 quote、页码、locator）。一条证据可被多条引用使用
Claim 断言 vs Answer 回答 回答是整体产出（含状态、模型、不确定度）；断言是回答内部可独立核验的句子，每条断言绑定 0..n 条引用
Policy 策略 vs PermissionGrant 权限授权 权限授权回答"谁能访问哪个资源"（subject/resource/action）；策略回答"系统在什么条件下允许外发与生成回答"（是否强制引用、是否逐文件确认、置信度阈值）。修改入口与生命周期不同
Notification 通知 vs AuditEvent 审计事件 通知面向用户、可标记已读（UC12）；审计事件是只增不改的留痕（BR12 的逐文件确认记录），不可删改
ParseRun 解析运行 vs IndexingRun 索引运行 前者产出页面与内容块（IR），后者在 IR 之上建全文/向量索引；两者可分别失败与重试
Document 文档 vs DocumentVersion 文档版本 文档是逻辑实体；版本是一次导入的内容快照（source_hash 唯一），引用与笔记必须绑定版本而非文档

2. 每个 AI 回答是否必须经过权限、证据契约和引用校验？

结论：是，且是强制链，无旁路。 三道关都挂在 AI 回答用例上，且都是 <<include>>（必经）而非 <<extend>>（可选）。

关 检查内容 规则 结构落点 图
① 权限 检索 / 缓存 / 上下文组装 / 模型调用前完成文档权限过滤 BR01 PermissionGrant；Answer ..> PermissionGrant : gate A6（第一步即权限过滤）、A3
② 证据契约 授权允许外发 + 版本有效 + 契约完整 + 置信度达策略阈值 BR02 Evidence；Answer ..> Evidence : requires contract；Policy.confidence_threshold A3（evidence_checked）
③ 引用校验 引用必须来自本次 allow-list，服务端校验，不得自由生成页码 BR03、BR04 Claim、Citation；support_status 五值 A3（citation_checked）

"必经"的证据（不是靠文字承诺，是靠关系类型）

  • 用例图 V0.3：UC06 ..> Gate : <<include>>、UC06 ..> Cite : <<include>>、UC06 ..> UploadConfirm : <<include>>，UC07 同样三条——include 意味着执行宿主用例必然执行它；只有 Fallback 是 extend（可选降级）。
  • 状态图 A2：正常流转链 requested → retrieving → evidence_checked → generating → citation_checked → answered，没有任何一步可以跳过；任一关不过就转入分支态（refused / needs_human_review / citation_invalid / local_evidence_only），而不存在"未校验但已是 answered"的路径。
  • 规约：UC06 主成功路径第 2/5 步、UC07 主成功路径第 2/5 步明确写出组装 Evidence Contract 与校验 claim/citation。

残余

  • 置信度阈值是策略参数（Policy.confidence_threshold），具体取值未定——依赖 TBD-8（供应商与 SLA）。建模期冻结的是"必须有这道关且阈值可配"，不是阈值数值。
  • 引用校验的失败判据（多大偏移算 locator_failed）未定，与 TBD-5（DOCX 页码策略）绑定。

R-02 裁决材料 · 核验引用（UC08）的宿主用例

  • 提交：2 组 · 郭谦
  • 日期：2026-10-20
  • 用途：评审会一页纸裁决件
  • 关联：11-需求模型V0.3-2组-阅读助手.md §2.1 R-02、2组修改说明.md §5、06-建模图-2组-阅读助手/底稿-PlantUML/用例图-V0.3.puml

1. 一句话说明

V0.2 用例图把「创建批注/笔记（UC09）」写成「核验回答引用（UC08）」的扩展（UC09 ..> UC08 : <<extend>>）。2 组认为这同时有两处错（宿主错 + 关系类型错），提出重挂方案；评审会需在下面两个方案中裁决其一。

两个方案都不改动任何用例的内容、参与者与主成功路径，只改用例图中的关系线。

V0.2 原状：  UC09 ..> UC08 : <<extend>>      （创建批注/笔记 扩展 核验回答引用）

2. 问题诊断

# 问题 说明
① 宿主（base）选错 <<extend>> 的含义是"扩展用例在特定条件下插入到基础用例中"。核验引用是用户在看到一条带引用的回答之后才会做的可选动作，其基础用例必然是被核验的两类回答用例——UC06 对文档/选中文本提问、UC07 生成摘要/要点，而不是 UC09。
② 关系类型误用 笔记与引用之间是数据关联，不是行为扩展：领域模型中 Note "0..*" --> "0..1" Answer、Citation、Evidence。V0.2 把它画成 <<extend>>，属于把"数据关系"画成了"行为关系"。

3. 方案对比

方案 A（2 组推荐）

移除：  UC09 ..> UC08 : <<extend>>
新增：  UC08 ..> UC06 : <<extend>>      （核验回答引用 扩展 对文档/选中文本提问）
        UC08 ..> UC07 : <<extend>>      （核验回答引用 扩展 生成摘要/要点）

方案 B（保守）

仅反向：UC09 ..> UC08 : <<extend>>  →  UC08 ..> UC09 : <<extend>>

对比

维度 方案 A（推荐） 方案 B（保守）
宿主是否选对（问题 ①） ✅ 是。宿主改为被核验的回答用例 UC06/UC07 ❌ 否。宿主仍是 UC09（笔记），核验引用仍挂在不该挂的用例上
关系类型是否修正（问题 ②） ✅ 是。移除 UC09↔UC08 的行为扩展，笔记与引用回归领域模型中的数据关联 ❌ 否。仍然把数据关联画成行为扩展，只是方向反了
与领域模型是否自洽 ✅ 自洽。Note → Answer/Citation/Evidence 为数据关联，图中不再出现 Note 的行为扩展 ❌ 冲突。图上说"核验引用扩展记笔记"，模型里两者并无行为依赖
改动的图形元素 2 增 1 删（3 条线） 1 条线反向
对用例内容/路径/参与者的影响 无 无
评审解释成本 需说明"本条超出原计划『修正关系方向』的表述，因为它是关系类型问题而非方向问题"（见下） 无需额外解释
风险 无技术风险；仅需评审接受"按语义重挂"这一表述扩展 语义站不住：若评审追问"核验引用为什么是记笔记的可选扩展"，无法给出合理回答

4. 两种方案的图示语差

方案 A：
  UC06 提问 ◁── <<extend>> ── UC08 核验引用
  UC07 摘要 ◁── <<extend>> ── UC08 核验引用
  UC09 笔记        （与 UC08 之间：无行为关系，改由领域模型 Note→Citation 承载）

方案 B：
  UC09 笔记 ◁── <<extend>> ── UC08 核验引用      （仅方向反了，宿主仍是 UC09）

5. 2 组建议

采用方案 A。 理由：

  1. 只有方案 A 同时修掉问题 ① 与 ②；方案 B 只改了箭头方向，两处错误都还在；
  2. 方案 A 与领域模型（Note / Answer / Citation 的数据关联）自洽，不需要在评审时为一张图单独辩护；
  3. 方案 A 不改变任何用例的行为，对需求内容零影响，改动只在图形表达层；
  4. 现 06-建模图-2组-阅读助手/底稿-PlantUML/用例图-V0.3.puml 已按方案 A 落稿，若裁决采用方案 B，2 组按裁决回改即可（成本 1 条线）。

需要评审会明确的一句话：R-02 的处理超出了原计划中"修正两处关系方向"的表述——UC09 与 UC08 之间是关系类型误用而非方向错误，故按语义重挂而非简单反向。
