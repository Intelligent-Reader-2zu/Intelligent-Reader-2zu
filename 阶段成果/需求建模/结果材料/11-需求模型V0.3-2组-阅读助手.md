## 1. 修订总览

| 编号 | 位置 | V0.2 原状 | V0.3 修订后 | 依据 |
|---|---|---|---|---|
| R-01 | 用例图 | `UC02 ..> UC01 : <<extend>>` | `UC01 ..> UC02 : <<include>>` | 导入文档**必然**触发处理与索引，属包含关系。原写法使"处理并索引"变成可选扩展，与 UC02 前置条件"文档已登记"矛盾 |
| R-02 | 用例图 | `UC09 ..> UC08 : <<extend>>` | 移除；改为 `UC08 ..> UC06 : <<extend>>`、`UC08 ..> UC07 : <<extend>>` | 核验引用是对"提问/摘要"回答的**可选扩展行为**（宿主应为 UC06/UC07）；笔记与引用之间是**数据关联**（领域模型中 Note ⟶ Citation），不是行为扩展关系 |
| R-03 | 领域模型 | `Workspace "1" o-- "1..*" User` | `User "0..*" -- "1..*" Workspace : 成员` | 组合关系意味着用户被工作区独占且每区必含≥1 用户。用户是系统一等实体（可登录、可发起 Query），不应被工作区拥有；且共享工作区仍属 TBD-1 未决项，模型不应提前锁死 |
| R-04 | 领域模型 | `Query "1" --> "1" DocumentSet` | `Query "0..*" --> "0..1" DocumentSet` | 单文档问答（UC06 对当前文档提问）不构成文档集合，V0.2 强制 1 个 DocumentSet 使单文档场景无法建模 |
| R-05 | 领域模型 | `ExportJob "1" --> "1..*" Note` | `ExportJob "0..*" --> "0..*" Note` | UC10 允许仅导出摘要或引用，此时导出任务不含任何 Note；V0.2 强制 1..* 与此冲突 |
| R-06 | 领域模型 | 缺索引类 | 新增 `IndexingRun`、`Index`，并建立与 `DocumentVersion` / `ContentBlock` 的关联 | BR06 要求删除/撤权/版本变化后**索引**与引用一并标记 stale，需要索引级对象承载 `version_id` 与 `stale`；NFR-05 要求保留解析溯源字段 |
| R-07 | 领域模型 | 缺模型与策略类 | 新增 `ModelConfig`、`Policy` | UC11（配置模型与隐私边界）、BR02（证据包准入）、BR12（逐文件确认）、FR-09 在 V0.2 中只以 `Workspace.policy` 一个字符串承载，无法落到可实现的实体 |
| R-08 | 领域模型 | 缺通知与审计类 | 新增 `Notification`、`AuditEvent` | UC12 需要通知对象；BR02/BR12 的"本次明确确认"与"可审计"要求需要有事件记录载体 |

**统计**：共 8 条修订，其中用例图 2 条（R-01、R-02）、领域模型 6 条（R-03 ~ R-08）。

## 2. 修订后用例图

源文件：[`06-建模图-2组-阅读助手/底稿-PlantUML/用例图-V0.3.puml`](./06-建模图-2组-阅读助手/底稿-PlantUML/用例图-V0.3.puml)

### 2.1 关系修订明细

**R-01｜导入 → 处理并索引（extend 改为 include）**

```text
V0.2：  UC02 ..> UC01 : <<extend>>      （处理并索引 扩展 导入文档）
V0.3：  UC01 ..> UC02 : <<include>>     （导入文档 包含 处理并索引）
```

修订理由：

1. UC02 的前置条件本身写的是"文档已登记"，说明处理总是在导入之后发生，是**必经步骤**而非可选扩展；
2. 格式不支持、权限不足等失败分支仍由 UC02 的异常路径承载（`ParseRun.status = failed`），不影响 include 的成立；
3. 原写法会让读者误解为"用户可以只导入不处理"，与 UC03"查看文档状态"依赖处理结果的设定冲突。

**R-02｜核验引用的宿主用例（重新挂载 extend）**

```text
V0.2：  UC09 ..> UC08 : <<extend>>      （创建批注/笔记 扩展 核验回答引用）
V0.3：  UC08 ..> UC06 : <<extend>>      （核验回答引用 扩展 对文档/选中文本提问）
        UC08 ..> UC07 : <<extend>>      （核验回答引用 扩展 生成摘要/要点）
        移除 UC09 ..> UC08
```

修订理由：

1. 核验引用是用户在**看到一条带引用的回答之后**才会做的可选动作，其宿主必然是被核验的两类回答用例 UC06 与 UC07；
2. 创建批注/笔记与核验引用之间是**数据关联**（领域模型中 `Note "0..*" --> "0..1" Answer`、`Citation`、`Evidence`），V0.2 把它写成行为扩展属于关系类型误用；
3. 该修订不影响 UC08 的参与者与主成功路径，仅修正其挂载位置。

> 说明：此条相对 [2 组建模任务分工书 §4](../过程材料/2组建模任务分工书.md) 中"修正两处关系方向"的表述略有扩展——UC09 与 UC08 之间不是方向问题而是关系类型问题，故按语义重挂而非简单反向。**如组内评审认为应保守处理（仅反向为 `UC08 ..> UC09 : <<extend>>`），可在评审会上提出由组长裁决。**

### 2.2 未改动的部分

以下内容与 V0.2 完全一致：5 个参与者及其与用例的连接、UC01–UC12 与 4 个内部用例（UploadConfirm / Gate / Cite / Fallback）的清单、`UC06/UC07` 对 `Gate`/`Cite`/`UploadConfirm` 的 include、`UC06/UC07` 对 `Fallback` 的 extend。

## 3. 修订后领域模型

源文件：[`06-建模图-2组-阅读助手/底稿-PlantUML/领域模型-V0.3.puml`](./06-建模图-2组-阅读助手/底稿-PlantUML/领域模型-V0.3.puml)

### 3.1 多重度修订明细

**R-03｜User 与 Workspace**

```text
V0.2：  Workspace "1" o-- "1..*" User
V0.3：  User "0..*" -- "1..*" Workspace : 成员
```

- 由**组合**（`o--`）改为**关联**（`--`）：用户不是工作区的组成部分；
- 多重度由 `1..*` 改为两侧显式标注：一个用户可参与多个工作区，一个工作区至少有 1 名用户；
- ⚠️ "一个用户能否同时属于多个工作区"本身是 **TBD-1 未决项**（V0.2 §11.1）。本修订只解除"用户被工作区独占"的硬约束，**不主张共享工作区已确认**。

**R-04｜Query 与 DocumentSet**

```text
V0.2：  Query "1" --> "1" DocumentSet
V0.3：  Query "0..*" --> "0..1" DocumentSet
```

- `0..1`：单文档问答（UC06 对当前文档提问）不构造 DocumentSet；
- `0..*`：同一个文档集合可被多次查询复用。

**R-05｜ExportJob 与 Note**

```text
V0.2：  ExportJob "1" --> "1..*" Note
V0.3：  ExportJob "0..*" --> "0..*" Note
```

- 导出范围可为纯摘要或纯引用（UC10 主成功路径），此时 Note 数量为 0；
- 同一条笔记可出现在多次导出任务中。

### 3.2 新增类（R-06 ~ R-08）

| 类 | 关键属性 | 关联 | 覆盖的需求 / 规则 |
|---|---|---|---|
| **IndexingRun** 索引运行 | run_id、engine_version、config_hash、status、warnings | `DocumentVersion "1" o-- "0..*" IndexingRun` | NFR-05（溯源字段）、UC02（处理状态可见） |
| **Index** 索引 | index_id、version_id、index_type(fulltext/vector/hybrid)、build_status、built_at、stale | `IndexingRun "1" --> "0..*" Index`；`Index "0..*" --> "1..*" ContentBlock` | BR06（stale 传播）、FR-03（全文/语义检索） |
| **ModelConfig** 模型配置 | config_id、provider、model_name、routing_policy、allow_cloud | `Workspace "1" o-- "0..*" ModelConfig`；`Answer "0..*" --> "0..1" ModelConfig` | UC11、FR-09、BR02 |
| **Policy** 策略 | policy_id、policy_version、require_citation、require_per_file_consent、confidence_threshold、export_scope | `Workspace "1" o-- "0..*" Policy`；`PermissionGrant ..> Policy : 依据` | BR02、BR12、NFR-08、SURVEY-007/008 |
| **Notification** 通知 | notification_id、type、resource_ref、created_at、read | `User "1" -- "0..*" Notification`；→ Answer / ParseRun | UC12、FR-10 |
| **AuditEvent** 审计事件 | event_id、event_type、actor、resource_ref、occurred_at | `User "1" -- "0..*" AuditEvent`；→ Answer / ExportJob | BR02、BR12（"本次明确确认"须可追溯）、UC10 |

**设计说明**：

- `Index` 显式保留 `version_id` 与 `stale`，是为了让 BR06 的"删除/撤权/版本变化 → 索引与引用同时失效"可以落到具体对象上，而不是散落在文字规则里；
- `Policy` 与 `PermissionGrant` 分开：`PermissionGrant` 回答"谁能访问哪个资源"，`Policy` 回答"系统在什么条件下允许外发与生成回答"，两者生命周期与修改入口（UC11）不同；
- `AuditEvent` 与 `Notification` 分开：前者是**只增不改的审计留痕**（BR12 的逐文件确认记录），后者是**面向用户的状态提醒**（可标记已读），语义与保留策略不同。

### 3.3 未改动的部分

`Workspace / DocumentSpace / Document / DocumentVersion / ParseRun / Page / ContentBlock / PermissionGrant / DocumentSet / Query / Evidence / Answer / Claim / Citation / Note / ExportJob` 共 16 个原有类的属性与其余关联均保持 V0.2 原样；`PermissionGrant ..> DocumentVersion : filters`、`Answer ..> PermissionGrant : gate`、`Answer ..> Evidence : requires contract` 三条依赖保持不变。
