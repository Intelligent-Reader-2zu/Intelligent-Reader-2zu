## 1. 修订总览

| 编号 | 位置 | V0.2 原状 | V0.3 修订后 | 依据 |
|---|---|---|---|---|
| R-01 | 用例图 | `UC02 ..> UC01 : <<extend>>` | `UC01 ..> UC02 : <<include>>` | 导入文档**必然**触发处理与索引，属包含关系。原写法使"处理并索引"变成可选扩展，与 UC02 前置条件"文档已登记"矛盾 |
| R-02 | 用例图 | `UC09 ..> UC08 : <<extend>>` | 移除；改为 `UC08 ..> UC06 : <<extend>>`、`UC08 ..> UC07 : <<extend>>` | 核验引用是对"提问/摘要"回答的**可选扩展行为**（宿主应为 UC06/UC07）；笔记与引用之间是**数据关联**（领域模型中 Note ⟶ Citation），不是行为扩展关系 |

## 2. 修订后用例图

源文件：[`06-建模图-2组-阅读助手/底稿-PlantUML/用例图-V0.3.puml`](./06-建模图-2组-阅读助手/底稿-PlantUML/用例图-V0.3.puml)

### 2.1 关系修订明细

**R-01｜导入 → 处理并索引（extend 改为 include）**

```text
V0.2：  UC02 ..> UC01 : <<extend>>      （处理并索引 扩展 导入文档）
V0.3：  UC01 ..> UC02 : <<include>>     （导入文档 包含 处理并索引）
```

修订理由：

1. UC02 的前置条件本身写的是"文档已登记"，说明处理总是在导入之后发生，是**必经步骤**而非可选扩展；
2. 格式不支持、权限不足等失败分支仍由 UC02 的异常路径承载（`ParseRun.status = failed`），不影响 include 的成立；
3. 原写法会让读者误解为"用户可以只导入不处理"，与 UC03"查看文档状态"依赖处理结果的设定冲突。

**R-02｜核验引用的宿主用例（重新挂载 extend）**

```text
V0.2：  UC09 ..> UC08 : <<extend>>      （创建批注/笔记 扩展 核验回答引用）
V0.3：  UC08 ..> UC06 : <<extend>>      （核验回答引用 扩展 对文档/选中文本提问）
        UC08 ..> UC07 : <<extend>>      （核验回答引用 扩展 生成摘要/要点）
        移除 UC09 ..> UC08
```

修订理由：

1. 核验引用是用户在**看到一条带引用的回答之后**才会做的可选动作，其宿主必然是被核验的两类回答用例 UC06 与 UC07；
2. 创建批注/笔记与核验引用之间是**数据关联**（领域模型中 `Note "0..*" --> "0..1" Answer`、`Citation`、`Evidence`），V0.2 把它写成行为扩展属于关系类型误用；
3. 该修订不影响 UC08 的参与者与主成功路径，仅修正其挂载位置。

> 说明：此条相对 [2 组建模任务分工书 §4](../过程材料/2组建模任务分工书.md) 中"修正两处关系方向"的表述略有扩展——UC09 与 UC08 之间不是方向问题而是关系类型问题，故按语义重挂而非简单反向。**如组内评审认为应保守处理（仅反向为 `UC08 ..> UC09 : <<extend>>`），可在评审会上提出由组长裁决。**

### 2.2 未改动的部分

## 3. 修订后领域模型

源文件：[`06-建模图-2组-阅读助手/底稿-PlantUML/领域模型-V0.3.puml`](./06-建模图-2组-阅读助手/底稿-PlantUML/领域模型-V0.3.puml)

### 3.1 多重度修订明细

**R-03｜User 与 Workspace**

```text
V0.2：  Workspace "1" o-- "1..*" User
V0.3：  User "0..*" -- "1..*" Workspace : 成员
```

- 由**组合**（`o--`）改为**关联**（`--`）：用户不是工作区的组成部分；
- 多重度由 `1..*` 改为两侧显式标注：一个用户可参与多个工作区，一个工作区至少有 1 名用户；
- ⚠️ "一个用户能否同时属于多个工作区"本身是 **TBD-1 未决项**（V0.2 §11.1）。本修订只解除"用户被工作区独占"的硬约束，**不主张共享工作区已确认**。

**R-04｜Query 与 DocumentSet**

```text
V0.2：  Query "1" --> "1" DocumentSet
V0.3：  Query "0..*" --> "0..1" DocumentSet
```

- `0..1`：单文档问答（UC06 对当前文档提问）不构造 DocumentSet；
- `0..*`：同一个文档集合可被多次查询复用。

**R-05｜ExportJob 与 Note**

```text
V0.2：  ExportJob "1" --> "1..*" Note
V0.3：  ExportJob "0..*" --> "0..*" Note
```

- 导出范围可为纯摘要或纯引用（UC10 主成功路径），此时 Note 数量为 0；
- 同一条笔记可出现在多次导出任务中。

### 3.2 新增类（R-06 ~ R-08）

| 类 | 关键属性 | 关联 | 覆盖的需求 / 规则 |
|---|---|---|---|
| **IndexingRun** 索引运行 | run_id、engine_version、config_hash、status、warnings | `DocumentVersion "1" o-- "0..*" IndexingRun` | NFR-05（溯源字段）、UC02（处理状态可见） |
| **Index** 索引 | index_id、version_id、index_type(fulltext/vector/hybrid)、build_status、built_at、stale | `IndexingRun "1" --> "0..*" Index`；`Index "0..*" --> "1..*" ContentBlock` | BR06（stale 传播）、FR-03（全文/语义检索） |
| **ModelConfig** 模型配置 | config_id、provider、model_name、routing_policy、allow_cloud | `Workspace "1" o-- "0..*" ModelConfig`；`Answer "0..*" --> "0..1" ModelConfig` | UC11、FR-09、BR02 |
| **Policy** 策略 | policy_id、policy_version、require_citation、require_per_file_consent、confidence_threshold、export_scope | `Workspace "1" o-- "0..*" Policy`；`PermissionGrant ..> Policy : 依据` | BR02、BR12、NFR-08、SURVEY-007/008 |
| **Notification** 通知 | notification_id、type、resource_ref、created_at、read | `User "1" -- "0..*" Notification`；→ Answer / ParseRun | UC12、FR-10 |
| **AuditEvent** 审计事件 | event_id、event_type、actor、resource_ref、occurred_at | `User "1" -- "0..*" AuditEvent`；→ Answer / ExportJob | BR02、BR12（"本次明确确认"须可追溯）、UC10 |

**设计说明**：

- `Index` 显式保留 `version_id` 与 `stale`，是为了让 BR06 的"删除/撤权/版本变化 → 索引与引用同时失效"可以落到具体对象上，而不是散落在文字规则里；
- `Policy` 与 `PermissionGrant` 分开：`PermissionGrant` 回答"谁能访问哪个资源"，`Policy` 回答"系统在什么条件下允许外发与生成回答"，两者生命周期与修改入口（UC11）不同；
- `AuditEvent` 与 `Notification` 分开：前者是**只增不改的审计留痕**（BR12 的逐文件确认记录），后者是**面向用户的状态提醒**（可标记已读），语义与保留策略不同。

### 3.3 未改动的部分

`Workspace / DocumentSpace / Document / DocumentVersion / ParseRun / Page / ContentBlock / PermissionGrant / DocumentSet / Query / Evidence / Answer / Claim / Citation / Note / ExportJob` 共 16 个原有类的属性与其余关联均保持 V0.2 原样；`PermissionGrant ..> DocumentVersion : filters`、`Answer ..> PermissionGrant : gate`、`Answer ..> Evidence : requires contract` 三条依赖保持不变。

### 2.2 易混术语辨析（必须区分）

| 易混对 | 区别 |
|---|---|
| **Evidence 证据** vs **Citation 引用** | 证据是原文片段本身；引用是回答里指向某条证据的落点（含 quote、页码、locator）。一条证据可被多条引用使用 |
| **Claim 断言** vs **Answer 回答** | 回答是整体产出（含状态、模型、不确定度）；断言是回答内部可独立核验的句子，每条断言绑定 0..n 条引用 |
| **Policy 策略** vs **PermissionGrant 权限授权** | 权限授权回答"谁能访问哪个资源"（subject/resource/action）；策略回答"系统在什么条件下允许外发与生成回答"（是否强制引用、是否逐文件确认、置信度阈值）。修改入口与生命周期不同 |
| **Notification 通知** vs **AuditEvent 审计事件** | 通知面向用户、可标记已读（UC12）；审计事件是只增不改的留痕（BR12 的逐文件确认记录），不可删改 |
| **ParseRun 解析运行** vs **IndexingRun 索引运行** | 前者产出页面与内容块（IR），后者在 IR 之上建全文/向量索引；两者可分别失败与重试 |
| **Document 文档** vs **DocumentVersion 文档版本** | 文档是逻辑实体；版本是一次导入的内容快照（source_hash 唯一），引用与笔记必须绑定版本而非文档 |

**主成功路径**

1. 用户明确选择一个或多个文件（系统不遍历目录、不自动读取工作区，BR11）。
2. 系统校验文件格式与访问权限。
3. 系统计算 `source_hash`，登记 `Document` 与 `DocumentVersion`；若同一 `source_hash` 已存在有效版本，则不重复创建（SPEC §3.2）。

5. 系统向用户返回 `document_id`、`version_id`、`parse_run_id`（SPEC §7 `/documents/import`）。
6. 系统生成导入完成通知（`Notification`）。

| 编号 | 触发条件 | 系统响应 | 结果状态 |
|---|---|---|---|
| 1a | 格式不支持 | 明确提示不支持及原因，不读入其他文件 | 不创建版本 |
| 1b | 权限不足 | 提示权限原因，不读入其他文件 | 不创建版本 |
| 3a | 同一 `source_hash` 已存在有效版本 | 不重复创建，提示已存在并定位到既有版本 | 复用既有 `DocumentVersion` |
| 4a | 解析任务创建失败 | 记录错误码，提示可重试或删除任务 | `ParseRun.status = failed` |

| 触发事件 | 解析任务被调度 |

**主成功路径**

1. 系统调度解析任务，文档状态由 `queued` 进入 `processing`。
2. Local Parser/OCR 解析文档并产出统一中间表示（IR）：`Page`（`physical_page`、`page_label`、`asset_ref`）与 `ContentBlock`（`text`、`section_path`、`char_start/end`、`bbox`、`confidence`）（SPEC §3.2）。
3. 解析器写回 `ParseRun`（`parser_version`、`config_hash`、`status`、`warnings`）；全部内容块置信度达标时，状态由 `processing` 进入 `parsed`。
4. 系统在 IR 之上创建 `IndexingRun` 与 `Index`，记录 `version_id`、`index_type`（全文 / 向量）与权限范围。
5. 索引构建成功，状态进入 `indexed`；系统生成处理完成通知（`Notification`）（BR15）。
6. 用户可随时查询处理状态、进度、警告与错误码（SPEC §7 `GET /documents/{id}/status`）。

**异常与降级路径**

| 编号 | 触发条件 | 系统响应 | 结果状态 |
|---|---|---|---|
| 2a | 扫描件 OCR 低置信 | 保留原页/截图并标注风险，**不承诺精确结构化问答**（BR07） | `ocr_low_confidence` → `needs_review`（`ERR-201`） |
| 2b | 双栏 / 表格 / 公式结构不确定 | 同上 | `layout_uncertain` → `needs_review`（`ERR-202`） |
| 3a | 解析器异常或文件损坏 | 记录错误码与重试次数，提示可重试或删除任务 | `failed`（`ERR-203`） |
| 3b | 解析超时 | 同上 | `failed`（`ERR-205`） |
| 4a | 全文索引构建失败 | 保留已解析结果，提示"当前仅可原文阅读" | `parsed`（索引未完成，`Index.build_status = failed`）（`ERR-206`） |
| 4b | 向量索引引擎缺失或未启用 | 降级为全文检索，明确提示 | `indexed`（仅全文）（`ERR-207`） |
| 5a | 用户删除失败任务 | 任务标记删除，不再占用队列 | `deleted`（`ERR-208`） |

**后置条件**：生成 IR、结构候选与索引；处理状态、进度与警告可见（关闭浏览器后仍可查）。

**关联**

- 业务规则：BR07、BR15
- 功能需求：FR-02
- 非功能需求：NFR-05（溯源字段）、NFR-11（处理耗时须记录）
- 领域对象：ParseRun、Page、ContentBlock、IndexingRun、Index、Notification
- 图：A1（状态图·文档处理）、A5（时序图·导入-解析-索引）

### UC06 对当前文档/选中文本提问

**主成功路径**

| 项 | 内容 |
|---|---|
| 用例编号 | `UC12` |
| 用例名称 | 查看处理/核验通知 |
| 主要参与者 | Reader |
| 前置条件 | 系统产生事件 |
| 触发事件 | 解析完成、低置信、摘要完成、引用失效或待复核状态产生 |

**主成功路径**

1. 系统事件产生时创建 `Notification`，字段为 `type`、`resource_ref`、`created_at`、`read`（初始 `false`）。
2. 通知类型覆盖：解析完成、低置信 / 结构不确定（`needs_review`）、摘要完成、引用失效（`stale`）、引用定位失败（`citation_invalid`）、待人工复核（`needs_human_review`）。

4. 用户点击通知，系统按 `resource_ref` 跳转到对应对象（`ParseRun` / `Answer` / `Citation` / `DocumentVersion`），并展示**可解释状态与错误码**。

**异常与降级路径**

| 编号 | 触发条件 | 系统响应 | 结果状态 |

| 1a | 同一事件重复产生通知 | 按（`type` + `resource_ref`）去重，不重复投递 | 单条通知 |
| 3a | 事件延迟到达 | 按 `created_at` 排序并标注延迟，不隐藏 | 通知照常可见 |
| 4a | 通知指向的对象已失效 | 展示失效原因与错误码，**不跳转到空对象** | 提示失效（`ERR-303` 等） |

**后置条件**：用户可查看并标记已读；`Notification` 可改，而 `AuditEvent` **只增不改**（术语表 §2.2）。

**关联**

- 业务规则：BR04、BR15
- 功能需求：FR-10（含 SRS-FR11）
- 非功能需求：—（基线未列）
- 领域对象：Notification、AuditEvent、ParseRun、Answer、Citation
- 图：A5（时序图·导入-解析-索引）、领域模型

## 0. 为什么需要这张表

基线 §11 是 12 条**光秃秃的问题列表**：没有问题影响哪个模型元素、没有验证方式、没有责任人，也没有说"建模期能不能先关掉"。

后果是这份清单在评审时无法被使用——它既不能说明"哪些问题已经在建模期定下了保守口径、不阻塞交付"，也不能说明"哪些问题必须在测试阶段实测"。本表把它收口成可检查的四段式：**问题 → 影响落点 → 验证方案 → 建模期口径**，并给出关闭状态。

## 1. 收口口径

每条 TBD 的**建模期状态**取三态之一：

| 状态 | 含义 |
|---|---|
| `建模期已关闭` | 建模阶段即可给出确定结论，不需要实测 |
| `降级关闭` | 无法在建模期实测，但已选定**保守且不锁死未来**的建模口径；数值/细节留待验证阶段 |
| `建模期未关闭` | 必须依赖实测或外部输入（访谈、压测），建模期只能标注风险、不能结论 |

> 判断原则：**只要基线语义已足以支撑建模决策，就关闭；只要是"数值/阈值/供应商"这类实测项，就降级关闭或标记未关闭。** 建模期不阻塞，但清单必须能被测试阶段直接接管。

## 2. 通用约定

- **结果状态**一律使用术语表 §1.4 的冻结状态名；`—` 表示该错误不落到状态机，只返回错误响应（多为**前置校验失败**，尚未产生状态对象）。
- **重试**三态：
  - `不可重试`——条件不可变（如格式不支持）；
  - `可重试`——原样重试有效（如解析失败、模型超时）；
  - `改善后可重试`——需用户先改条件（权限、范围、路径、网络）。
- **可见性**：建议对用户只展示语义提示，错误码仅进日志与 `/status` 接口（见 §6）。

## 0. 这份文件补的是什么

启动包 §5 明确"第一轮模型评审时必须回答"这 9 个问题，但 1 组基线交付中**没有对应的回答件**——需求模型 V0.2 按"参与者 / 用例 / 规则 / 类 / 状态 / NFR / TBD"分节组织，SRS 与 SPEC 按模块组织，两者都没有按评审问题组织过内容。评审时只能临场翻材料拼答案。

本文件即该回答件。每条按三段式写：

| 段 | 作用 |
|---|---|
| **结论** | 一句话给出"能不能过"，结论只能是"是 / 部分 / 否" |
| **证据** | 模型与文档里的具体落点（编号 + 文件名），评审可现场翻 |
| **残余** | 本问题**尚未关闭**的部分，指向 TBD 编号或缺口的登记位置 |

> 原则：**凡结论说"是"的，都能在仓库里指到具体编号；指不到的一律写进"残余"，不假装已解决。** 因此本文件的"残余"段与《TBD 收口表》《RTM》§5 缺口表是同一批内容的三个视角。

## 2. 每个 AI 回答是否必须经过权限、证据契约和引用校验？

**结论：是，且是强制链，无旁路。** 三道关都挂在 AI 回答用例上，且都是 `<<include>>`（必经）而非 `<<extend>>`（可选）。

| 关 | 检查内容 | 规则 | 结构落点 | 图 |
|---|---|---|---|---|
| ① 权限 | 检索 / 缓存 / 上下文组装 / 模型调用**前**完成文档权限过滤 | BR01 | `PermissionGrant`；`Answer ..> PermissionGrant : gate` | A6（第一步即权限过滤）、A3 |
| ② 证据契约 | 授权允许外发 + 版本有效 + 契约完整 + 置信度达策略阈值 | BR02 | `Evidence`；`Answer ..> Evidence : requires contract`；`Policy.confidence_threshold` | A3（`evidence_checked`） |
| ③ 引用校验 | 引用必须来自本次 allow-list，服务端校验，不得自由生成页码 | BR03、BR04 | `Claim`、`Citation`；`support_status` 五值 | A3（`citation_checked`） |

**"必经"的证据（不是靠文字承诺，是靠关系类型）**

- 用例图 V0.3：`UC06 ..> Gate : <<include>>`、`UC06 ..> Cite : <<include>>`、`UC06 ..> UploadConfirm : <<include>>`，UC07 同样三条——**include 意味着执行宿主用例必然执行它**；只有 `Fallback` 是 extend（可选降级）。
- 状态图 A2：正常流转链 `requested → retrieving → evidence_checked → generating → citation_checked → answered`，**没有任何一步可以跳过**；任一关不过就转入分支态（`refused` / `needs_human_review` / `citation_invalid` / `local_evidence_only`），而**不存在"未校验但已是 answered"的路径**。
- 规约：UC06 主成功路径第 2/5 步、UC07 主成功路径第 2/5 步明确写出组装 Evidence Contract 与校验 claim/citation。

**残余**

- 置信度阈值是策略参数（`Policy.confidence_threshold`），**具体取值未定**——依赖 TBD-8（供应商与 SLA）。建模期冻结的是"必须有这道关且阈值可配"，不是阈值数值。
- 引用校验的**失败判据**（多大偏移算 `locator_failed`）未定，与 TBD-5（DOCX 页码策略）绑定。

## 3. 文档解析不确定、云端不可用、无依据或过期证据时，系统是否仍有明确结果？

**结论：是。** 四类异常各自有**冻结的状态名 + 用户可见的提示语 + 错误码**，没有一类是"静默继续"。

| 异常类别 | 触发条件 | 结果状态（术语表 §1.4 冻结） | 错误码 | 用户看到什么 | 图 / 规则 |
|---|---|---|---|---|---|
| 文档解析不确定 | 扫描件 OCR 低置信 | `ocr_low_confidence` → `needs_review` | `ERR-201` | "识别置信度低，已保留原页/截图" | A1、A5、BR07 |
| 文档解析不确定 | 双栏/表格/公式结构不确定 | `layout_uncertain` → `needs_review` | `ERR-202` | "结构不确定，已保留原页/截图" | A1、A5、BR07 |
| 文档解析不确定 | 解析异常 | `failed` | `ERR-203` | "解析失败，可重试或删除任务" | A1、A5 |
| 云端不可用 | 模型超时或失败 | `model_failed` | `ERR-501`、`ERR-502` | 明确失败态，可重试 | A2、A3 |
| 云端不可用 | 无网络 / 用户拒绝外发 / 策略禁止 | `local_evidence_only` | `ERR-503`、`ERR-401`、`ERR-306` | "已按你的选择不调用云端模型" | A2、A3、BR12、BR13 |
| 无依据 | 检索后无可用证据 | `refused` | `ERR-510` | "无法从当前文档确认该问题"，**不得伪装成有依据回答** | A2、BR04、BR05 |
| 无依据（证据不足但非空） | 证据覆盖不足 | `needs_human_review` | `ERR-509` | "证据不足，请补充检索范围" | A2 |
| 过期证据 | 版本变化 / 撤权 / 删除传播未完成 | `stale` | `ERR-303`、`ERR-304`、`ERR-305` | "来源已变更，引用已标记失效" | A1、A3、BR06、UC08 |
| 引用定位失败 | 引用无法回到原文 / 引用不合规 | `citation_invalid` | `ERR-504`–`ERR-508` | **禁止显示为已核验答案**（同时给 `support_status = locator_failed`） | A2、A3、BR03、BR04、UC08 |

来源：《[V0.3-SPEC错误码表](./V0.3-SPEC错误码表.md)》（44 条，覆盖 `ERR-1xx`~`ERR-6xx` + `ERR-9xx`）。

**近似失败的兜底**：BR13 / NFR-09 规定**离线时阅读与基础检索仍可用**，AI 不可用不得导致阅读器整体不可用；BR15 规定长任务必须显示进度。所以"云端挂了"不是"产品挂了"。

**残余**

- 人工复核的**可接受等待时间**未定（TBD-3）；建模期只保证"复核状态可见且不需要实测就能判断进入复核"。
- 部分状态（`citation_invalid`、`ERR-5xx`）在 SPEC V1.0 中只被"要求存在"，具体取值由 2 组补建——见 W4 的 SRS/SPEC 返修清单。

## 4. 多文档检索是否显式选择授权范围，是否能够区分来源和冲突？

**结论：范围显式——是；区分来源——是；区分冲突——部分（规则在，可视化未细化）。**

**(1) 授权范围是显式的，不是系统推定的**

- 领域模型 R-04 把 `Query "1" --> "1" DocumentSet` 改为 `Query "0..*" --> "0..1" DocumentSet`：**单文档问答不构造集合**，多文档检索才需要集合，集合由用户选择。
- A6 活动图第一步就是"选择范围"，第二步才是权限过滤（BR01）。
- `DocumentSet` 定义（术语表 §2.1）："一次检索或问答的**显式**上下文范围，**由用户选择而非系统推定**"。
- NFR-06：多文档查询默认由用户显式选择授权集合。

**(2) 来源可区分**

BR08 要求多文档回答显示**来源、版本、时间与冲突**；A6 按来源分组返回结果；`Citation` 绑定 `evidence_id` → `Evidence` → `block_id` / 版本 / 页码（术语表 §2.2）。

**(3) 冲突部分**

BR04 的 `support_status` 五值中包含 `conflicting`（冲突），即"两条证据互相矛盾"有明确表示位；但**"冲突怎么展示给用户"尚未细化**（列表式？并排式？以哪条为准？）。

**残余**

- 单次查询规模上限 **20 份**是 **NFR-06 的候选值**，未实测（TBD-2）。RTM §5 已登记为缺口。
- **冲突可视化规则未细化**——RTM §5 未单列该缺口，**本文件作为新增缺口登记**：建议在 V0.3 合并时补一条界面级说明，或明确记为"实现期细化"。
- FR-11（跨知识库/跨项目问答）**不进一期**，所以"跨库冲突"不在本期范围。

## 5. 笔记、引用、回答和原文之间是否存在稳定关联？

**结论：是。** 四类对象之间的关联在领域模型中全部显式落类，且**稳定性靠绑定版本而非绑定文档**来保证。

**关联链（领域模型 V0.3 §3）**

```
原文            ContentBlock ──→ Page ──→ DocumentVersion ──→ Document
                   ↑                （reference 的稳定锚点）
回答            Answer ──→ Claim ──→ Citation ──→ Evidence ──→ ContentBlock
                                       ↑
笔记            Note ──────────────────┘
```

| 关联 | 承载方式 | 规则 |
|---|---|---|
| Note ↔ 原文 | `Note` 关联 `document_version_id` + `block_id` | BR09 |
| Note ↔ 回答/引用 | R-05 修订后 `ExportJob "0..*" --> "0..*" Note`；`Note ⟶ Citation` 为**数据关联**（R-02 明确它不是行为扩展） | BR09、R-02 |
| Citation ↔ 原文 | `Citation.evidence_id` → `Evidence` → `ContentBlock` → `bbox` / `char_start-end` | BR03、NFR-01 |
| 稳定性 | 引用与笔记**必须绑定 `DocumentVersion` 而非 `Document`**（术语表 §2.2「Document vs DocumentVersion」） | BR06、BR09 |
| 失效可见 | 版本变化/撤权/删除 → `DocumentVersion.stale` + `Index.stale`，笔记与引用提示复核 | BR06、BR09 |
| 可回溯 | `Index` 显式保留 `version_id` 与 `stale`（R-06 新增），使 stale 传播能落到具体对象 | BR06 |

**残余**

- **定位漂移的容忍阈值与修复策略未定**（原文改版后笔记锚点偏移多少算失效）：属实现细节，与 TBD-5 相关。
- `Citation.locator` 的最终策略（DOCX 用视觉页码还是段落/标题路径）**未定**（TBD-5）。

## 7. 是否将 PDF、DOCX/Markdown、PPTX 的格式优先级转化为分阶段验收范围，XLSX/TXT 采用何种受限支持策略？

**结论：是，且已转成可判定的规则与提示语。**

| 格式 | 一期定位 | 依据 | 验收方式 |
|---|---|---|---|
| **PDF** | `Must` —— 首要输入格式，含文本型与扫描型 | SURVEY-002-Q2（18/20 选择）；V0.2 §10 FR-02；NFR-13 | 解析测试组：文本 PDF 结构化 + 扫描 PDF 走 OCR 与低置信分支 |
| **DOCX / Markdown** | 高优先级（一期） | SURVEY-002-Q2（各 11/20）；NFR-13 | 解析测试组：结构化提取 + 目录/章节树 |
| **PPTX** | 候选扩展（`Should`，**受限**） | SURVEY-002-Q2（10/20）；V0.2 §10 "PPTX 进入候选扩展范围" | 可导入登记；不承诺页面布局与演讲者注释的精确结构化 |
| **XLSX / TXT** | **受限支持** | SURVEY-002-Q2（各 4/20）；V0.2 §2.2 | 可导入登记并做基础文本提取；**明确提示"不承诺结构化问答"**，不作为一期验收项 |

**"受限支持"落到模型上的三个可判定点**

1. **不装死**：不支持的格式必须**明确提示**，不得静默失败（NFR-13）。
2. **不越界**：提示格式不支持时**不得继续遍历目录或读取其他文件**（BR11；规范化为 `ERR-101`/`ERR-102` 的前置校验，见错误码表 §2 说明）。
3. **低置信可降级**：PPTX/XLSX 等复杂版面走 BR07 —— 保留原页/截图与风险标记，`ERR-201`/`ERR-202` → `needs_review`，**不承诺精确结构化问答**。

**残余**

- PPTX / XLSX / TXT 的**一期边界线**与"复杂表格/公式/演示文稿引用的可接受准确率"未定 → **TBD-10**（`降级关闭`：建模期按"受限支持 + 明确提示"处理）。
- Markdown 方言、表格、脚注、公式、代码块的支持范围未定 → **TBD-6**（`降级关闭`）。
- n=20 的偏好排序**不等于兼容承诺**（启动包 §1 证据分层表），不得把 18/20 读成"PDF 完整兼容"。

## 8. 云端和本地模型路径是否都默认逐文件确认外发，并为拒绝外发保留离线阅读/本地证据路径？

**结论：是——但必须先纠正这题的一个前提。** 一期的**云端路径有，本地模型路径没有**。

**(1) 先把术语说清（这题的前提本身有歧义）**

| 题目里的措辞 | 一期实际含义 |
|---|---|
| "本地模型路径" | ⚠️ **一期不存在本地大模型推理路径**：FR-12「本地生成模型问答」在 V0.2 §10 中被标注为**"明确不承诺"**，RTM §1.1 记为"范围外" |
| "本地证据路径" | ✅ 存在：拒绝外发后走 `local_evidence_only`——返回**本地证据与原文**，不生成"看似有依据"的模型回答（BR12、BR05） |

> 因此第 8 题的正确答案是："**云端路径逐文件确认；本地没有模型路径，但有本地证据/原文降级路径。**" 若照题目字面回答"两条路径都逐文件确认"，会凭空承诺一个不存在的本地推理能力。
> 附带风险：SURVEY-008-Q8 问的是"**所谓本地模型场景**"下的接受度（50% 接受询问 / 35% 不接受任何上传），V0.2 §2 已标注"**需验证产品术语理解**"——用户未必分得清"本地推理"与"本地证据降级"。本项**待访谈验证**（WP-D）。

**(2) 确认机制（云端路径）**

| 要求 | 落点 |
|---|---|
| 逐文件展示范围、模型服务与用途，取得**本次**明确确认 | BR12、NFR-08；`Policy.require_per_file_consent`；`UploadConfirm` 内部用例；A4 时序图 |
| **不得默认关闭**逐文件确认 | BR12；UC11 异常路径明写"逐文件外发确认不得被默认关闭"；错误码 `ERR-404`（"该策略不允许关闭逐文件确认"，不可重试） |
| 默认不自动上传、不自动遍历 | BR11；`ModelConfig.allow_cloud` |
| 确认记录可追溯（"本次"的含义） | `AuditEvent`（只增不改）；`ERR-401` 记录 `decision=rejected` |

**(3) 拒绝外发后的降级链**

`用户拒绝` → `Fallback`（extend）→ `local_evidence_only` → 仍返回**本地检索到的原文与证据**，并提示"已按你的选择不调用云端模型"（`ERR-401`）。

**(4) 离线兜底与"路径分离"**

- BR13 / NFR-09：离线时**阅读、打开、已建索引的基础检索仍可用**，AI 入口显示明确降级状态，**不得导致阅读器整体不可用**。
- A9 界面导航图中，门控控件落点被固定在 `settings`（BR11/BR12/BR02/BR10）与 `answer-more`（BR03/BR06）两个页面，避免确认入口散落。

**残余**

- 云端模型的供应商、地区、费用、数据保留与长期 SLA 全部未定 → **TBD-8**（`建模期已关闭`：建模期只冻结"必须逐文件确认"这一机制）。
- 用户能否正确理解"本地证据降级 ≠ 本地模型"未验证 → 与 WP-D 访谈绑定；若访谈推翻，需回到 §2.4 参与者与 FR-12 的口径。

# R-02 裁决材料 · 核验引用（UC08）的宿主用例

- 提交：2 组 · 郭谦
- 日期：2026-10-20
- 用途：评审会一页纸裁决件
- 关联：[`11-需求模型V0.3-2组-阅读助手.md`](./11-需求模型V0.3-2组-阅读助手.md) §2.1 R-02、[`2组修改说明.md`](../过程材料/2组修改说明.md) §5、[`06-建模图-2组-阅读助手/底稿-PlantUML/用例图-V0.3.puml`](./06-建模图-2组-阅读助手/底稿-PlantUML/用例图-V0.3.puml)

## 1. 一句话说明

V0.2 用例图把「创建批注/笔记（UC09）」写成「核验回答引用（UC08）」的扩展（`UC09 ..> UC08 : <<extend>>`）。2 组认为这**同时有两处错**（宿主错 + 关系类型错），提出重挂方案；评审会需在下面两个方案中裁决其一。

**两个方案都不改动任何用例的内容、参与者与主成功路径，只改用例图中的关系线。**

```
V0.2 原状：  UC09 ..> UC08 : <<extend>>      （创建批注/笔记 扩展 核验回答引用）
```

## 2. 问题诊断

| # | 问题 | 说明 |
|---|---|---|
| ① | **宿主（base）选错** | `<<extend>>` 的含义是"扩展用例在特定条件下插入到基础用例中"。核验引用是用户在**看到一条带引用的回答之后**才会做的可选动作，其基础用例必然是被核验的两类回答用例——**UC06 对文档/选中文本提问**、**UC07 生成摘要/要点**，而不是 UC09。 |
| ② | **关系类型误用** | 笔记与引用之间是**数据关联**，不是行为扩展：领域模型中 `Note "0..*" --> "0..1" Answer`、`Citation`、`Evidence`。V0.2 把它画成 `<<extend>>`，属于把"数据关系"画成了"行为关系"。 |

## 3. 方案对比

### 方案 A（2 组推荐）

```
移除：  UC09 ..> UC08 : <<extend>>
新增：  UC08 ..> UC06 : <<extend>>      （核验回答引用 扩展 对文档/选中文本提问）
        UC08 ..> UC07 : <<extend>>      （核验回答引用 扩展 生成摘要/要点）
```

### 方案 B（保守）

```
仅反向：UC09 ..> UC08 : <<extend>>  →  UC08 ..> UC09 : <<extend>>
```

### 对比

| 维度 | 方案 A（推荐） | 方案 B（保守） |
|---|---|---|
| 宿主是否选对（问题 ①） | ✅ 是。宿主改为被核验的回答用例 UC06/UC07 | ❌ 否。宿主仍是 UC09（笔记），核验引用仍挂在不该挂的用例上 |
| 关系类型是否修正（问题 ②） | ✅ 是。移除 UC09↔UC08 的行为扩展，笔记与引用回归领域模型中的数据关联 | ❌ 否。仍然把数据关联画成行为扩展，只是方向反了 |
| 与领域模型是否自洽 | ✅ 自洽。`Note → Answer/Citation/Evidence` 为数据关联，图中不再出现 `Note` 的行为扩展 | ❌ 冲突。图上说"核验引用扩展记笔记"，模型里两者并无行为依赖 |
| 改动的图形元素 | 2 增 1 删（3 条线） | 1 条线反向 |
| 对用例内容/路径/参与者的影响 | 无 | 无 |
| 评审解释成本 | 需说明"本条超出原计划『修正关系方向』的表述，因为它是关系类型问题而非方向问题"（见下） | 无需额外解释 |
| 风险 | 无技术风险；仅需评审接受"按语义重挂"这一表述扩展 | **语义站不住**：若评审追问"核验引用为什么是记笔记的可选扩展"，无法给出合理回答 |

## 4. 两种方案的图示语差

```text
方案 A：
  UC06 提问 ◁── <<extend>> ── UC08 核验引用
  UC07 摘要 ◁── <<extend>> ── UC08 核验引用
  UC09 笔记        （与 UC08 之间：无行为关系，改由领域模型 Note→Citation 承载）

方案 B：
  UC09 笔记 ◁── <<extend>> ── UC08 核验引用      （仅方向反了，宿主仍是 UC09）
```

## 5. 2 组建议

**采用方案 A。** 理由：

1. 只有方案 A 同时修掉问题 ① 与 ②；方案 B 只改了箭头方向，两处错误都还在；
2. 方案 A 与领域模型（`Note` / `Answer` / `Citation` 的数据关联）**自洽**，不需要在评审时为一张图单独辩护；
3. 方案 A 不改变任何用例的行为，**对需求内容零影响**，改动只在图形表达层；
4. 现 [`06-建模图-2组-阅读助手/底稿-PlantUML/用例图-V0.3.puml`](./06-建模图-2组-阅读助手/底稿-PlantUML/用例图-V0.3.puml) 已按方案 A 落稿，若裁决采用方案 B，2 组按裁决回改即可（成本 1 条线）。

**需要评审会明确的一句话**：R-02 的处理**超出了原计划中"修正两处关系方向"的表述**——UC09 与 UC08 之间是关系**类型**误用而非方向错误，故按语义重挂而非简单反向。

## 5. 提交信息规范

格式：

```
<类型>(<范围>): <描述> [<任务编号>]
```

**类型**（取其一）

| 类型 | 含义 |
|---|---|
| feat | 新增内容（新图、新章节） |
| fix | 修正基线中的错误 |
| docs | 文档类变更 |
| chore | 杂项（目录、配置、说明） |
| test | 测试相关 |

**范围**：`2组/图形`、`2组/文档`、`2组/界面`、`2组/访谈`、`2组/模型`

**任务编号**：对应任务分工书的编号，如 `WP-A/A1`

**示例**

```
docs(2组/文档): 补全 UC01-UC12 用例规约 [WP-B/B1]
feat(2组/图形): 新增文档处理与回答生成状态图 [WP-A/A1-A2]

chore(2组): 新增 2 组建模任务分工书与 Git 协作规范
```

**硬要求**
- 描述用中文，写清"做了什么"，不许出现"更新""修改""提交"这类无信息量的词；
- 一次提交只做一件事；
- `git add` 必须**按文件名加**，禁止 `git add -A` / `git add .`。

# 智能笔记助手需求建模 · AI 使用说明

- 文档版本：V1.0
- 编制：郭谦（2 组组长）
- 日期：2026-10-17
- 用途：说明建模阶段 AI 辅助的范围与人工确认边界，供评审核查

> 本文件与 [`2组修改说明.md`](../过程材料/2组修改说明.md)、[`版本记录.md`](../过程材料/版本记录.md) 三者同为 1 组《02-需求建模汇报PPT》第 8 页承诺但未随仓库交付的材料，由 2 组补齐。

---

## 1. 总体原则

1. **AI 用于提速，不用于定责任**。AI 产出一律视为**初稿**，进入仓库的每个结论都由组员人工确认后才生效。
2. **AI 不接触受限材料**。用户访谈记录、姓名/学号/联系方式、未授权样本原文**一律不输入任何外部模型**（与 BR10、调研任务书 §12 一致）。
3. **编号体系与术语冻结**。AI 不得自造用例编号、状态名、业务规则编号——所有编号以 1 组 V0.2 基线为唯一来源。

---

## 2. 本轮（WP1 / WP6）的 AI 使用范围

| 环节 | AI 参与方式 | 人工确认内容 |
|---|---|---|
| 基线材料解析 | 辅助提取 1 组 `.docx` / `.pptx` / `.pdf` 交付材料的正文，形成结构化摘要 | 组员核对提取结果与原文件一致 |
| 图关系复核 | 辅助比对用例图关系与用例前置条件，**提出**可疑关系（如导入与处理的 extend/include 归属） | 组员判断是否成立、是否修改 |
| 领域模型复核 | 辅助检查领域类与业务规则的覆盖关系，**提出**缺失类（Index/Policy/Notification 等） | 组员确认新增类是否必要、属性是否与 SPEC 冲突 |
| 修订方案起草 | 辅助起草 R-01 ~ R-08 的修订说明与依据文本 | 组员逐条核对依据、裁决争议项（见第 4 节） |
| `.puml` 源文件生成 | 辅助生成 PlantUML 代码 | 组员本地渲染预览，确认图规范、无语法错误 |
| 文档成文 | 辅助起草修改说明、版本记录、AI 使用说明、汇报 PPT 骨架 | 组员确认事实准确性与表述口径 |

**结论**：AI 的贡献集中在**检索、比对、初稿生成**；**关系取舍、编号口径、交付口径**全部由人工决定。

---

## 3. AI 不参与的部分
